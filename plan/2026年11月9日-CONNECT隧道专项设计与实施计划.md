# CONNECT 隧道专项设计与实施计划

**目标**：在不破坏现有 HTTP origin-form/SOCKS 出站路径的前提下，交付标准 HTTP/1.1 CONNECT 入站隧道。

## 已完成的 RED/GREEN 契约

- 新增 `gateway/src/connect.rs`。
- `parse_connect_authority` 严格接受域名、IPv4、方括号 IPv6 + 1..65535 端口。
- 严格拒绝路径、query、fragment、userinfo、空格、控制字符、未括号 IPv6、非法端口和错误 bracket。
- RED：实现缺失时 6 个调用点编译失败。
- GREEN：5 个解析测试通过，Clippy 通过。
- `gateway::parse_connect_target` 已作为 gateway 层稳定转发入口，但尚未接入生产监听。

## Pingora 0.9 取证结论

- `HttpServerOptions::allow_connect_method_proxying` 仅解除默认 405；Pingora 明确说明 CONNECT 会改变 request-response flow 和 framing，因此默认关闭。
- 现有 `ProxyHttp` 的 `proxy_upstream_filter` 返回 false 只会进入普通 `finish`，不是流所有权接管。
- HTTP/1 Upgrade 使用 `HttpTask::UpgradedBody`，仅在合法 Upgrade/101 流程下可用，不应伪造为 CONNECT。
- `ServerSession::stream()` 只提供借用；现有高层回调没有将下游 HTTP/1 session 无损消费为原始流的 API。
- `ServerApp::process_new(Stream, ShutdownWatch)` + `services::listening::Service` 可承接原始 TCP/TLS 流，适合独立 CONNECT listener。
- `Listeners::add_tls` / `TlsSettings` 可实现 TLS 入站，但 TLS 入站和 CONNECT 隧道应分开验收。

## 推荐架构

### 首版：独立 CONNECT listener

使用 Pingora `ServerApp` 监听单独的 `CONNECT_ADDR`（默认关闭或独立端口），流程为：

1. 接收 `Stream`，只处理 HTTP/1.1 CONNECT。
2. 有界读取请求头，拒绝非 CONNECT、非 authority-form、非零 Content-Length、Transfer-Encoding、Expect 等未定义 framing。
3. 使用 `parse_connect_authority` 解析目标。
4. 复用租户认证、并发槽、节点候选过滤与凭据护栏；CONNECT 目标不从普通 Host 路由语义猜测。
5. 选择节点并建立上游连接：HTTP 代理用显式 CONNECT 握手；SOCKS 节点复用 `socks_handshake::establish`。
6. 上游握手成功后向客户端写 `HTTP/1.1 200 Connection Established`，不发送 Content-Length/Transfer-Encoding，并 flush。
7. 保留客户端请求头后已读的预读字节；将其先发往上游，再执行 `copy_bidirectional`。
8. 处理 EOF、半关闭、取消、空闲超时、最大寿命、关停、部分字节计量和最终租户槽释放。
9. 隧道开始传输后不得重试/切换节点。

### 上游连接模型

- `HttpPeer` 的 `Proxy` 字段在当前 Pingora 0.9 是 UDS next-hop 语义，Windows 不适合作为远程代理 TCP 地址；CONNECT 客户端应使用新的 TCP `Stream` + 受控 HTTP CONNECT handshake，或复用 SOCKS 建链。
- 不关闭 TLS 证书校验；上游代理 TLS 必须有显式代理地址/SNI/信任配置。
- 目标 TLS 由客户端在 CONNECT 成功后自行完成，网关不解密目标内容。

## 测试阶段

### 阶段 A：纯协议

- 解析合法/非法 authority。
- 请求 framing 拒绝。
- 目标 host/port 不回显密钥。

### 阶段 B：上游 HTTP CONNECT

- 本地 TCP mock 代理收到正确 CONNECT authority 和允许的认证头。
- 上游非 2xx 时客户端不收到 200。
- 上游 200 与首段隧道 payload 同次写入时，首段字节不丢失。
- 下游请求头与首段 payload 同次写入时，首段字节不丢失。

### 阶段 C：双向传输

- 双向 echo。
- 客户端半关闭后仍收到上游尾数据。
- 上游半关闭后客户端仍可发送并收到已有尾数据。
- 建链超时、空闲超时、最大寿命、取消和关停。
- 连接成功后不再重试；失败节点记录与遥测状态正确。

### 阶段 D：项目语义

- 缺失/错误 API Key 返回正确状态且不出站。
- 租户并发槽成功、失败、取消均只释放一次。
- 上下行字节计量定义明确。
- 免费节点携带 Authorization/Cookie 时拒绝。
- CONNECT 日志只记录目标摘要或哈希，不记录完整敏感路径/凭据。

### 阶段 E：TLS 入站

- 独立 TLS listener 使用显式证书和私钥。
- 证书加载失败启动即失败，不降级成明文。
- TLS CONNECT 与明文 CONNECT 使用同一业务隧道实现。
- 客户端证书校验和 SNI 另设配置，不默认开启 MITM 解密。

## 不在首版范围

- HTTP/2 CONNECT / Extended CONNECT。
- HTTP/3、CONNECT-UDP、MASQUE。
- 目标 HTTPS 解密/MITM。
- 将 CONNECT 伪装成 WebSocket Upgrade。
- 将标准 CONNECT 接入当前普通 Pingora `ProxyHttp` 回调而不解决流所有权和预读字节。

## 验收条件

- 普通 HTTP 与现有 SOCKS 翻译桥回归全绿。
- CONNECT 协议矩阵与预读字节测试通过。
- 真实标准客户端完成 CONNECT 后 TLS 请求。
- 失败、半关闭、取消、超时和计量测试通过。
- 无新增凭据日志路径。
- 明确记录支持协议、监听地址、认证方式和未支持的 HTTP/2/3 边界。
