## 1. P0：阻塞步骤 54 收口的两个缺陷

步骤 54 的方向是对的（探针结果回灌选路），但当前实现有两个问题，
**不修就收口，等于把一个"看起来闭环、实际会漏"的能力写进文档**。

### P0-1 用"近似计数器"做正确性闸门

**现象**
热路径用计数器做短路：

- `router.rs:347-352` `is_active_unhealthy()`：
  `if active_unhealthy_count.load() == 0 { return false }`
- `router.rs:357` `active_unhealthy_len()`（指标 gauge）读**同一个**计数器
- `router.rs:489` 安全阀也用同一个计数器：`unhealthy + 1 >= eligible ⇒ 拒绝摘除`

**证据：计数器会低估**

`sweep_active_health()` 在 `router.rs:428-434` 把过期条目累加到 `expired`，
**循环结束后**才统一递减。递减时锁已释放，窗口期内该条目可能被
`record_probe_failure()`（`router.rs:459`）重新标记为摘除态并 `fetch_add(1)`：

```
T1 sweep:      iter_mut 命中 X → 置 None，expired=1，释放分片锁
T2 failure(X): 看到 None（跳过"已过期"分支）→ 重新置 Some，fetch_add(1)
T1 sweep:      dec(expired=1)      ← 减掉的这条此刻是"已摘除"状态
```

结果：计数器比真实值**少 1**。`store_nodes()`（`router.rs:961-988`）的
`removed_active` 是同一模式，同一风险。

**两个后果，方向相反但都很坏**

1. **放过不健康节点**：计数被减到 0 后，`is_active_unhealthy` 直接短路返回
   `false`，**已判定摘除的节点继续接流量**——这恰好是步骤 54 要消灭的行为。
2. **击穿安全阀**：安全阀用 `unhealthy + 1 >= eligible` 判断"再摘一个就没了"。
   计数低估 ⇒ 判断不成立 ⇒ 允许继续摘 ⇒ **可能摘到全池 503**，
   而安全阀存在的唯一理由就是防这个。
3. **指标同时失真**：gauge 读同一计数器，`active_probe_unhealthy_nodes`
   会显示 0，排障时看不到任何异常。

**为什么这不是"理论竞态"**
`janitor` 的 sweep 与 prober 的在飞探测**本来就是并发的**（prober 每 tick
开头/结尾各 sweep 一次，janitor 另有节拍）。触发不需要人为构造。

**修法（两行级改动，不是重构）**

- 热路径短路改用 `self.active_health.is_empty()`——**精确**且仍是 O(分片数)；
  计数器降级为"仅供 gauge 展示"的近似值，不再参与任何判断。
- sweep / store_nodes 末尾把计数器**重算**（`store(实际扫描值)`）而不是增量递减。
  条目规模是"池内节点数"（百级），60s 一次的全扫成本可忽略。

**验收（可执行）**
1. 新增并发压力测试：sweep 与 `record_probe_failure` 交叉 10 万次后，
   断言 `active_unhealthy_len() == 手工扫描的 Some 条目数`。
2. 红测有效性：把修法回退（改回 `== 0` 短路 + 增量递减），该测试必须判红。
3. 断言语义：构造"计数被低估"的确定场景（可直接注入计数器），
   断言 `is_active_unhealthy` 仍返回 `true`。

> 判据来自本仓既有教训（OPT-R17/步骤 51）：**测试必须证明行为，不能自证**。
> 所以验收不能只写"计数器等于 X"，必须写"节点不会被选中"。

### P0-2 全池探测的副作用没有配套治理

**现象**
`probe_candidates()`（`router.rs:383`）返回**全部** `weight > 0` 节点，含免费池。
这是正确修复（否则摘除即永不恢复），但带来两个未被计划覆盖的后果：

| 后果 | 说明 | 取证 |
| --- | --- | --- |
| 日志风暴 | 免费池节点大量为死，每轮每节点一条 `warn!` | `main.rs` 步骤 54 分支：每个 `Dead` 都 `log::warn!` |
| 阈值对免费档结构性失效 | 免费池地址进出会清空 `active_health` 条目（`router.rs:979-985`），连续失败计数归零 | 免费池 TTL 1800s（`free_pool.rs:2631`），阈值 3×60s=180s，**多数情况下够用，但节点掉出再回来即重置** |

**方向（不是"少探测"，是"分层"）**
1. **分层采样**：付费/托管节点 100% 探测；免费池按比例抽样（如 20%）+
   轮转游标，保证 N 轮内全覆盖。省的是探测预算与日志，不牺牲恢复能力。
2. **日志聚合**：单节点 `Dead` 降为 `debug`，每 tick 输出一条汇总
   （`dead 137/210 (paid 2/8)`），付费节点异常仍逐条 `warn`。
3. **文档写明边界**：主动健康对"地址稳定的付费节点"有效，对高频换血的免费池
   只能降低噪声、不能根治——**这一句要写进 `CAPABILITY-AUDIT.md` §4**，
   否则下一轮又会有人把它当"免费池也有健康闭环"来引用。

**验收**
- 一轮 200 节点 tick 的 `log/gw.err` 增量 < 20 行（当前会到百行量级）；
- 付费节点失败仍逐条可查；
- 抽样策略有单测：游标轮转 N 轮后覆盖率 = 100%。

## 2. P1：五个"不会红但会骗人"的缺口

这一组的共同特征：**CI 全绿、文档自洽、问题只在真实排障/真实接入时暴露**。

### P1-1 `trace_id` 只在遥测里，不在日志里

- 生成：`gateway.rs:852-860`；落库：`gateway.rs:1106`（`TelemetryEvent`）。
- `grep -c trace_id gateway.rs` = 5，**没有一处出现在 `log::` 宏里**。

**后果**：ClickHouse 里查到一条 502，想去 `log/gw.err` 看上下文——只能靠时间戳
猜；反过来也一样。一个已经有全链路 trace_id 的系统，**排障时用不上它**，
这是最典型的"能力已建、价值未兑现"。

**方向**：`warn!`/`error!` 级别统一带 `trace_id`（热路径 `info!` 可选，避免每行
一次 `String` 克隆）。注意本仓装的是 `env_logger`（无 `tracing` subscriber），
所以**不要**引入 `tracing` span——步骤 49 已经踩过这个坑并留档。

**验收**：构造一次上游失败，`gw.err` 中该行含 `trace_id=...`，且该值能在
ClickHouse 同一条记录中检索到（双源对账，口径同 `EXEC_LOG` 步骤 41）。

### P1-2 前端 1888 行、7 个页面，零测试、零 CI

- `web/admin/package.json` 只有 `dev/build/preview`，**无 test 脚本**。
- `.github/workflows/ci.yml` 四个 job（gates / static-checks / windows-powershell
  / supply-chain）**没有任何 npm 步骤**（`grep web/ ci.yml` 无命中）。
- 现有唯一验证：`log/admin_ui_walkthrough/` 的人工截图走查。

**后果**：后端契约一变（如 `/nodes` 返回裸数组、错误体 `{error, code}`），
前端可能静默崩，CI 仍然全绿。这是当前**唯一一个完全不在门禁内的交付物**。

**方向（成本低、收益确定）**
1. 新增 `web` job：`npm ci && npx tsc --noEmit && npm run build`（10 行 YAML）。
2. Playwright 冒烟 3 条：登录失败提示、节点列表渲染、新增节点后列表出现。
   用 `page.route()` mock `/api/v1`，不需要起后端。
3. 契约锁定：前端 `zod` 已在依赖里（`package.json`），把 API 响应 schema 显式
   写出来，让"后端改字段"在前端编译期/运行时立刻可见。

### P1-3 Windows 上不跑任何 Rust 测试

- `windows-powershell` job（`ci.yml:357-475`）只做 PSScriptAnalyzer + PS 5.1 解析。
- 源码中平台相关分支 9 处，其中 `main.rs:1275` `default_grace_secs(cfg!(windows))`
  正是 OPT-R14 那个"300 秒自杀" P0 的修复点。

**后果**：Windows 是主开发平台（`README` 快速开始就是 PowerShell），
但 Windows 专属逻辑在 CI 里**只被静态门覆盖**（`check_windows_lifetime.py`
断言"修复没被回退"，不验证"行为正确"）。

**方向**：windows-latest 加一步 `cargo test --locked --workspace --lib`。
若担心时长，先只跑 `main::tests` + `node_registry::tests`（平台相关性最高），
其余留 Linux job。**不要**为了省 CI 时间把这条做成"仅手动"——它挡的是 P0 级回退。

### P1-4 文档"结构性过期"没有门禁

- `docs/ARCHITECTURE.md`（9-25）、`COMPONENTS.md`（9-24）、`DATAFLOW.md`（9-26）、
  `SYSTEM-ARCHITECTURE.md`（9-26）、`USAGE.md`（9-29）自 10 月起未再改动，
  而 10-26 落了节点热更新与主动探测。
- `DATAFLOW.md` 把 prober 写成 `set_quarantine`，**代码里并不存在这个动作**
  （步骤 54 计划 §3 自己已承认，选择"改文档"而非"改语义"）。
- `tools/check_doc_consistency.py` 只匹配数字（`COUNT_RE`），**不校验结构声明**。

**方向**：把已经证明有效的"双向结构化比对"模式（`check_admin_routes_documented.py`）
复制到架构文档：`DATAFLOW.md`/`COMPONENTS.md` 里出现的模块名必须能在
`gateway/src/*.rs` 找到，反之每个 `src/*.rs` 必须被至少一处文档提及。
**只比对结构化清单，不做全文 grep**——OPT-R17 的教训是全文 grep 会被自己的
说明文字满足而假绿。

**反例保护**：新门必须先跑通"注入一个幽灵模块名 → 判红 → 还原 → 绿"。

### P1-5 决策质量不可度量（最大杠杆，也是最容易被忽略的）

这是本报告唯一一条**不是修 bug** 的建议，但长期价值最高。

**现状**：项目差异化是 LinUCB 选路，而所有验收都是"**选得动**"，不是"**选得好**"：

| 已有验收 | 证明了什么 | 没证明什么 |
| --- | --- | --- |
| OPT-R13 1500 次活流量（3/3 命中） | 不永久锁死 | 成功率是否优于加权随机 |
| 步骤 41：45.9% free 成功率 | 供给可用 | 换策略后是否更好 |
| `--release bandit` 17 测试 | 数学正确、<200ns | 线上收益 |

**可用的原料已经齐了**：ClickHouse 有 `out_ip`/`tier`/`status`/`latency`/`provider`/
`trace_id`（`telemetry.rs`、`analytics.rs`、`0001_init.sql`），
`docs/PERF_BASELINE.md` 也有压测脚手架。**缺的只是"回放"这一层。**

**方向：`tools/replay/`（离线策略回放台）**
1. 从 ClickHouse 拉一段真实请求序列（`trace_id` 排序，含 target_domain/tier/status）。
2. 同一序列分别跑：**LinUCB（当前参数）／加权随机／轮询／固定最优节点**。
3. 输出：成功率、每节点命中分布、`free` 档占比、P50/P99 时延、
   "本可避免的失败"（存在可用节点却选了失败节点）计数。
4. 形成 `docs/ROUTING_BASELINE.md`，作为选路类改动的**准入证据**：
   没有回放报告的选路改动不合并。

**为什么值得先做**：它把 R13/R14/R41 这种"仿真 + 手工活流量"的验证方式
升级为可复现基线，之后每次动 `bandit.rs`/`router.rs` 都能立刻回答
"这次改动让成功率涨了还是跌了"。**没有它，选路优化的收益永远是自述。**

**验收**：回放工具能在 5 分钟内跑完 10 万条历史请求；对 R13 的修复版本
与回退版本能复现出方向一致的差异（这是工具的**有效性**证明，不是功能演示）。

## 4. 明确**不**建议做的事

1. **不要再加静态门**。已有 15 道，边际收益递减，而每道门本身要维护、
   要防"被自己的注释满足"（OPT-R17 已踩）。新增门只给 P1-4 这一条（因为它是
   现有门的**结构性缺口**，不是加码）。
2. **不要为凑数字加单测**。341 个测试的瓶颈不是数量，是**鉴别力**——
   步骤 51 那个 `assert!(ADMIN_TIMEOUT_SECS > 0)` 就是数量涨了、质量为零的样本。
3. **不要在 CONNECT 落地前碰 PAC**。步骤 54 计划 §0 已取证：Pingora 0.9 只给
   CONNECT 放行开关，不给隧道数据面；先 PAC 会得到"浏览器能配代理、但上不了网"。
4. **不要现在做集群调度**。在单实例的租户持久化与配置热更新都没做完时，
   集群只会把"单点配置不一致"放大成"多点不一致"。

## 5. 建议的迭代顺序

排序原则：**先把"会骗人"的修掉，再建"能证明"的能力，最后扩"能接入"的场景。**

| 轮次 | 主题 | 内容 | 收口标志 |
| --- | --- | --- | --- |
| **R18-A**（立即） | 步骤 54 正确收口 | P0-1 计数器竞态 + P0-2 分层探测/日志聚合；同步基线 341；更新 `CAPABILITY-AUDIT` §4 与 `DATAFLOW.md` | 并发压力测试红→绿；`gw.err` 每 tick < 20 行；文档三处（审计/数据流/基线）与代码一致 |
| **R18-B** | 可验证性补洞 | P1-2 前端 CI + P1-3 Windows Rust 测试 + P1-1 trace_id 入日志 | CI 新增 2 个 job 全绿；一次失败请求的日志与 CH 记录可按 trace_id 互查 |
| **R18-C** | 决策可度量 | P1-5 回放台 + `docs/ROUTING_BASELINE.md` | 10 万条回放 < 5 分钟；能复现 R13 修复前后的方向差异 |
| **R19** | 产品闭环 | CONNECT 隧道 → TLS 入站 → PAC（三步各自独立验收，**不许合并成一步**） | 真实浏览器经网关访问 HTTPS 站点成功 |
| **R20** | 持久化与多实例 | P2-2 租户写穿、配置热更新扩展、P2-4 | 重启后余额/配额不变；两实例配置一致 |

**为什么 R18-A 必须先行**：步骤 54 一旦按现状收口，`CAPABILITY-AUDIT.md` 会写上
"主动健康闭环 ✅"，而实际存在"计数低估 ⇒ 坏节点继续接流量 + 安全阀失效"的路径。
**这正是本仓反复出现的"声明即失实"**（OPT-R17 的原始病灶），只是这次病灶在代码里，
不在依赖清单里。

### P1-5 选路回放台（本批杠杆最大的一条）

**解决的问题**：此前所有选路验收只证明「选得动」——OPT-R13 的 1500 次活流量证明不锁死、
步骤 41 的 45.9% 证明供给可用、17 个 bandit 测试证明数学正确——**没有一条证明「选得好」**。
于是「这次改动让选路变好了吗」只能靠作者自述。

**做法**：`tools/routing_replay.py`（纯标准库；d=4 手写 4×4 运算，不引 numpy——CI 的
static-checks 只装 python3，跑不起来的工具等于不存在）。基于日志的离线策略评估：
先用日志拟合两级收缩的结果模型（`(节点,域名) → 节点全局 → 全局`，`PRIOR_STRENGTH=5`），
再让四个策略在同一请求序列上决策、采样结果、按生产 `compute_reward` 同口径算奖励。

**结果**（合成样本 600 条 / 4 节点 / 3 域名 / seed 20261027）：

| 策略 | 成功率 | 相对轮询 | 可避免失败 |
| --- | ---: | ---: | ---: |
| `round_robin` | 29.7% | — | 385 (64.2%) |
| `weighted` | 30.8% | +1.1pp | 394 (65.7%) |
| `linucb` | 52.2% | **+22.5pp** | 180 (30.0%) |
| `oracle`（作弊上界） | 77.0% | +47.3pp | 0 (0.0%) |

三条可执行结论：① LinUCB 确实在学习（不是"能跑"，是"选得更好"）；② 距上界仍差 **24.8pp**，
即约 1/4 流量选错了——这是下一轮选路优化的**具体目标**，而不是笼统的"继续调 alpha"；
③ P99 已与 oracle 持平（249ms vs 249ms）⇒ 瓶颈在**成功率**不在时延，方向应是"少选错"。

**三类偏差已写进脚本头部与 `docs/ROUTING_BASELINE.md`**：支持偏差（未探索过的组合只能靠先验）、
相关当因果（模型学的是"日志策略选它时它成功了多少次"）、采样而非期望（保留方差以维持区分度）。
定位明确：**回归护栏 + 方向判断，不是线上收益预测器**。

**锁漂移两把锁**：
- `tools/check_replay_parity.py` —— Python 镜像 vs Rust 生产实现，黄金向量由**生产实现自己生成**
  （`print_replay_parity_vectors`，`#[ignore]`），不是手写期望值（否则同一个理解错误会同时通过两份断言）。
  容差 1e-12，实测最大差异 `3.33e-16`；变异自测扰动 `alpha` 1e-3 必须判红。
- `tools/check_routing_baseline.py` —— 文档 §4 表格必须**逐格等于**回放台可复现输出。
  实测四种漂移全红：改成功率 0.1pp / 改样本条数 / 改 seed / 删 oracle 行。

**准入规则**（写进 `ROUTING_BASELINE.md` §5）：选路改动合并前必须附改动前后两张表；
**没有回放对比的选路改动不合并**——这条的等价物是「性能改动必须附 benchmark」。

### P1-4 模块 ↔ 文档双向结构门

**落门时实测到的四类失真（此前 CI 全绿）**：

| # | 失真 | 危害 |
| - | ---- | ---- |
| ① | 标题声称「模块表（19 个）」，`gateway/src/` 实有 **24** 个 `.rs` | 漏掉的 `admin.rs` 是 1788 行的 Admin REST 面，读者按文档建心智模型会完全不知道它存在 |

**四类断言**（全部结构化比对，**不做全文 grep**——OPT-R17 实测过说明性注释恰好含目标 token
时门会对自己注入的回归报绿）：

| # | 断言 | 拦住的失真 |
| - | ---- | ---------- |
| A | `gateway/src/*.rs` 集合 == 中文表集合 == 英文表集合（双向分别报「漏登记」与「幽灵模块」） | ①②类结构缺失 |
| B | 标题「N 个」== 实际文件数 == 表格行数 | 标题与表格不同步 |
| C | 每行单测数 == 该文件 `#[test]`/`#[tokio::test]` 数；且**合计 == 基线通过数 + 忽略数 == 346** | 数字漂移、中英不一致 |
| D | 「关键 API」每个 token 必须在对应 `.rs` 里以整词出现 | ③类编造 |

**顺带的质量决策：删除「行数」列。** 它任何一行代码改动都会过期——设精确门禁则每个 PR 假红，
不设则它长期是假的。保留一个无法维护的数字等于保留一句对外失实（与本仓
`check_free_pool_contract.py` 的「不设会周期性假红的数量门」同一条结论）。体量信号改由
「单测」承担：它被断言 C 守住，且合计与权威基线自洽。

**维护方式**：`--refresh` 从源码回写单测列与标题计数（实测幂等）；新增/删除模块仍需手补整行
（职责与关键 API 是判断，不能自动生成）。

**变异自测**：漏登记模块 / 篡改单测数 / 编造 API 三处注入必须全红；另以临时文件实测
