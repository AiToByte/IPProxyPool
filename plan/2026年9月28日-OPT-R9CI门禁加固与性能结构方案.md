## 关键设计决策（先定口径，再动手）

### 决策 1：Prometheus 规则门——为何必须用 `promtool` 而非 YAML 解析

**现状（已实证）**：`ci.yml` 的规则门是

```yaml
- name: Prometheus rules syntax
  run: python3 -c "import yaml; d=yaml.safe_load(open('deploy/prometheus/rules.yml', encoding='utf-8')); assert d['groups'], 'no rule groups'"
```

`yaml.safe_load` 只能验**缩进与语法**，验不出 PromQL 语义。OPT-R7 B2 交付时我**亲身踩中**这一点：新写的 `ProviderForbiddenRatioHigh` 分母用了 `sum by (provider)(rate(proxy_requests_total[10m]))`，而该指标**没有 provider 标签**——YAML 门全绿，Prometheus 加载时 `health=ok`（语法合法），但**结果恒空/错配**。这类错误只有 `promtool check rules` 的类型检查能抓。

**修法：** 用 Prometheus 官方镜像跑 `promtool check rules`：

```yaml
- name: Prometheus rules (promtool: PromQL semantics, not just YAML)
  run: docker run --rm -v "$PWD/deploy/prometheus:/rules:ro" prom/prometheus:v2.53.0 \
        promtool check rules /rules/rules.yml
```

选 Prometheus 官方镜像而非 `apt-get install prometheus`（版本漂移、装整包慢、需 root）。**版本与 compose 里的 `prom/prometheus:v2.53.0` 严格一致**——用别的版本验可能放过或误报。

**配套（补第二条防线）：** 指标名逐个核对。`promtool` 验不了「指标名拼错」（PromQL 里未知序列是合法表达式）。故新增 `tools/check_promql_metrics.py`：从 `rules.yml` 抽取 LHS 指标名，对 `metrics.rs` 的 `# HELP` 清单核对，不一致即红。这正是 OPT-R7 B2 手工做过的核对，**固化成门**。

### 决策 2：SDK 编译验证——为何不能只 `node --check`

**现状（已实证）**：仓库**没有** `go.mod`/`.csproj`/`package.json`（已 `Get-ChildItem` 确认），CI 只跑 `python3 -m compileall`（覆盖 `.py`）。4 个 SDK 从未被编译或执行过。审阅已发现两处**确定破损**：

- `tools/ipp_sdk_go.go:19` 是 `package main`，而文件头 `:8` 的用法示例写 `import ipp "path/to/ipp_sdk_go"` —— Go **禁止 import 一个 `package main`**，该示例 100% 编译失败；
- `tools/ipp_sdk_dotnet.cs:10` 写 `dotnet run -- --self-test`，无 `.csproj` 时 `dotnet run` 直接报错。

**修法（分两层，如实标注能力边界）：**

- **语法/类型层**：Node → `node --check`；Go → 建**最小 `go.mod`**（`tools/sdk-go/go.mod`）后 `go vet`；.NET → 建最小 `.csproj` 后 `dotnet build`；Java → `javac`（JDK 自带，无需额外文件）。**Java/Go/.NET 都能真正编译**（给出类型级校验），Node 只能语法级（`--check` 不解析类型）——**此能力差异如实写进注释**。
- **不合并进主仓根**：SDK 是「独立小包 + 文件头自述用法」，塞进子目录会改变它们的用法示例语义。故建 `tools/sdk-go/go.mod` 与 `tools/sdk-dotnet/ipp_sdk.csproj`，用 `<Compile Include="..\ipp_sdk.go" />` 引用原文件（**不移动原文件**，保持对外路径不变）。

**边界：** 这些 `.csproj`/`go.mod` 是**为 CI 验证而存在**的最小壳，不是给用户用的发布包；`docs/USAGE.md` 口径需同步（如实登记）。

### 决策 3：`--locked` 与 lockfile 漂移——为何「加 flag」不够

**现状：** `ci.yml` 的 5 条 cargo 命令**全部无 `--locked`**；`gateway/Dockerfile:8` 的 `cargo build --release` 同样无。而 `docs/OPEN-SOURCE.md:22/63` 宣称「exact 版本锁 `Cargo.lock`，**构建可复现**」。

**只加 `--locked` 仍有洞**：它只保证**不修改** lockfile，不保证**lockfile 与 manifest 一致**（若有人改了 `Cargo.toml` 却忘了提交 `Cargo.lock`，`--locked` 会直接失败——这是好的）；但若有人**连 `Cargo.lock` 一起改错**（版本写错、checksum 不符），`--locked` 不会抓。因此补第二条：**`git diff --exit-code gateway/Cargo.lock`**，断言 CI 跑完后 lockfile 未被改动（用 `actions/cache` 也要小心 cache 命中时 cargo 是否重写 lockfile）。

### 决策 4：PowerShell 门——为何必须加 Windows job 而不只是升 Severity

**现状（两处缺陷）：**

1. `ci.yml:42` 是 `shell: pwsh` on `ubuntu-latest` = **Linux 上的 PowerShell 7**。而全部 6 个 `.ps1` 是 **Windows PowerShell 5.1 专属**（`#Requires -Version 5.1`；`install_watchdog.ps1:56` 用 `schtasks`；`ipp.ps1:93` 用 `Get-CimInstance Win32_Process`；`docs/USAGE.md:40-41` 改 `HKCU:\` 注册表）。PS 7 on Linux 拥有**不同的解析器与 cmdlet 集**，验不到生产真实执行环境。
2. `Invoke-ScriptAnalyzer -Severity Error` **把 Warning 全部丢掉**。而 `PSAvoidUsingPlainTextForPassword`、`PSUseDeclaredVarsMoreThanAssignments`、`PSAvoidGlobalVars` 等绝大多数规则是 **Warning 级**——CI 注释自称「脚本/配置漂移门」，实际只挡 Error。

**修法（两道）：**

- **A. 新增 `windows-latest` job**：用 **Windows PowerShell 5.1**（`shell: powershell`，不是 pwsh——GitHub 的 `powershell` shell 就是 5.1）跑：`PSScriptAnalyzer` ＋ **全部 `.ps1` 的语法解析断言**（`-ErrorAction Stop` 的 `[PSParser]::Tokenize`，能抓解析级错误而不执行脚本）。
- **B. 现有 Linux job 的 Severity 升到 `Warning`**，但**只对白名单规则报错**：全量 Warning 会有大量存量告警直接红。做法：`-Severity Warning -ExcludeRule <已知存量规则列表>`，并在 `.pscriptanalyzer` 配置里固化，使**新增**违规即红、存量不阻断（如实标注该取舍）。

### 决策 5：选路热路径 O(N) 分配——为何改「查表形态」而非「缓存 key」

**现状（已实证）：** `router.rs:172`

```rust
let key = format!("{}:{ip}", normalize_domain(domain));
```

`normalize_domain` 返回 `String`（本身一次分配），`format!` 再一次。而 `is_quarantined` 被 `is_node_quarantined` 调用，**后者又在 `matches` 的循环体内对每个节点调一次**（`router.rs:198`）⇒ 池大小 N 时**每请求 2N 次 `String` 分配**。免费池缺省 `FREE_MAX_NODES=2000` ⇒ 每请求约 4000 次堆分配。

同族的第二个热点：`gateway.rs` 的 `arm_for` 对每个候选 `node.addr.clone()`。

**为何不缓存 key（`domain:ip` → `String` 的 memo）：** 缓存需要 `DashMap` 查表（一次哈希 + 一次 `String` clone 用于查询）——**省不掉分配**，只是把 `format!` 换成 `clone`，且引入无界缓存（key 空间由客户端可控，见 R6 的隔离表键空间问题）。**得不偿失。**

**修法（结构性）：** 改**查表形态**。隔离表 key 是 `"{normalized_domain}:{ip}"`，其**前缀是归一后的 domain**、**后缀是 ip**。改为两级结构：

- 外层 `DashMap<String /*domain*/, DashMap<String /*ip*/, Instant>>`；
- `matches` 循环外做**一次** `normalize_domain`（O(1) 次分配），循环内只做 `quarantine_map.get(&domain)?.get(node.ip)` —— 两次哈希，**零分配**。

**语义等价性论证：** key 的**唯一性**由 `normalize_domain(domain) + ":" + ip` 拼接保证。归一化的目的是让 `Example.com.` 与 `example.com` 命中同一条目。两级结构下"同 domain 归一"与"同 ip 精确"两条不变 ⇒ 键空间与旧实现**一一对应**。需注意旧 key 的分隔符 `:`——若 domain 本身含 `:`，两级结构反而**更安全**（旧实现 `a:b` + ip 与 `a` + ip=`b`... 理论上可碰撞；实际 `normalize_domain` 已小写化 + 域名不含 `:`，无碰撞，但两级结构从根本上消除了该隐忧）。

**风险与取舍（如实标注）：** 隔离表原本是**扁平 key 便于 Redis 侧 `SETEX {key}` 与 `PUBLISH` 跨进程同步**（`circuit_breaker.rs` 消费 PubSub 后调 `set_quarantine`）。改两级只影响**内存查询形态**；`set_quarantine` 的对外接口（接受 domain + ip 两个参数）保持不变即可，Redis key 字符串生成保持扁平（跨进程协议不动）。**必须补单测锁定**：同 domain 不同 ip 隔离、跨 domain 同 ip 不隔离、大小写归一、删除语义。

### 决策 6：无界指标基数——为何「加上限 + 溢出桶」而非「截断丢弃」

**现状（已实证）：** `metrics.rs:335-343` `note_free_exit` 无条件 `entry(exit_ip.to_string()).or_insert_with(...)`，`free_exit_total: DashMap<String, AtomicU64>` **无容量上限**。免费代理出口 IP 是**公网随机 IP** ⇒ 标签取值空间无界 ⇒ 长期运行会同时撑爆网关内存（DashMap）与 Prometheus TSDB。

**为何不用「超过 N 就丢弃」：** 丢弃会让「某出口已用 1M 次」与「某出口仅 1 次」在 TopK 图上无法区分（后者已存在序列），造成**指标语义断层**。

**修法：溢出桶。** 保留原 key（`label` 维度，语义不变），另加一条 `label="__overflow__"` 序列承接超限后的计数。上限取 **512**（与 `FullChecker` 已有的 512 客户端缓存上限同量级，见 `free_pool.rs`）。`render` 恒渲染 `__overflow__`（值 0 时也渲染），使告警/图可判「是否已溢出」。

4. **不越界：** 零新生产依赖；C1 保持 `set_quarantine` 对外接口与 Redis key 格式不变（跨进程协议不动）；C2 保持既有 `free_exit_total{exit_ip="x"}` 渲染不变（只增溢出桶）。

## 执行后的增补说明（诚实记录，含三处「我错了」）

1. **A1 的实测结论推翻了 A2 的必要性论证方向（重要）**：
   原以为「`promtool` 抓标签错配 ⇒ 必须补 A2」。实测发现**恰好相反**：
   注入 OPT-R7 B2 的原始错误（`sum by(provider)` 匹配无 provider 标签的指标）后，
   `promtool check rules` 报 **`SUCCESS: 12 rules found` —— 完全放过**。
   它能抓的是 `histogram_quantile(0.99, "str")` 这类**参数类型**错。
   ⇒ A2 不是「补充」而是**唯一**能抓标签错配的手段。这个结论已写进
   `check_promql_metrics.py` 的文件头，避免后人误以为两者重复。
2. **零分配契约测试首版是假测试（三轮修正，如实记录）**：
   - 第 1 版：在**函数体内**定义 `Counting` 分配器但**没写 `#[global_allocator]`**
     ⇒ 计数器恒为 0、断言恒真。把 `format!` 塞回热路径后测试**仍然绿**。
   - 第 2 版：加上 `#[global_allocator]`（提到模块级）后测试**变红**——但根因是
     **并行测试线程的分配污染了进程级计数器**（`--test-threads=1` 下绿）。
   - 第 3 版（一度走错）：改成「并行下不误报、只打印提示」——实测这会让**真实
     回归溜过**：塞回 `format!` 后观察到 2000 次分配却被当作「污染」放行。
     **放宽判据的门禁等于没有门禁**，故回退到硬断言，改为把该测试标
     `#[ignore]` + CI 单独串行跑。
   - 最终 CI 命令需要**三个参数**才真正跑到它：`--test-threads=1`
     （排除并行噪声）、`--include-ignored`（否则 libtest 跳过它并报
     `0 passed` —— 门禁静默失效）、`--exact` 配**完整测试名**
     （只写函数名会过滤不命中，同样静默跑不到任何测试）。三个都实测确认过。
3. **B2 的设计从黑名单改为白名单（相对原计划的变更）**：原计划写
   `-Severity Warning -ExcludeRule <存量清单>`。实操中改为 `-IncludeRule` 白名单，
   理由：①本机装不上 PSScriptAnalyzer（PSGallery 缺 NuGet provider），
   **无法预先枚举存量告警**，黑名单会让 CI 首次运行直接红；②白名单规则集固定，
   不受 PSSA 版本新增规则影响；③语义更清晰。**代价**：未被列入白名单的规则
   （如 `PSAvoidUsingPositionalParameters` 之外的一批）仍不检查，覆盖面小于
   「全量 Warning」。同时顺手**锁定 PSSA 版本 1.21.0**，修掉审阅指出的
   PSGallery 供应链漂移风险。
4. **一次 YAML 陷阱（实测）**：step 名 `Prometheus rules (promtool: PromQL types, ...)`
   中的**冒号未加引号**，YAML 把它当映射分隔符 ⇒ **整份 workflow 解析失败**。
   已加引号并加注记。
5. **B1 的两个错误设计（已修）**：①误以为 `docker inspect -f` 的 `\"` 在 PowerShell
   双引号串里能转义（OPT-R8 已踩过一次同类坑，本轮在别处再现，说明**该坑值得
   记进检查清单**）；②误把「GBK 终端显示乱码」当成「ci.yml 注释被折断」——
   逐字节读文件后确认注释完好、YAML 合法、11 步齐全。**教训：控制台乱码
   不等于文件损坏，诊断前先做字节级验证**。
6. **C1 顺带修掉一个真实缺陷（计划内的预期收益，但值得单独记）**：旧扁平 key
   `"{domain}:{ip}"` 在 domain 含 `:` 时存在**碰撞**（`normalize_domain` 对 IPv6
   字面量产出 `::1`）。这不是理论风险——单测 `normalize_domain_cases` 本就锁定了
   `normalize_domain("a:b") == "a:b"`，说明该形态在真实输入中可能出现。
   两级结构以 `DashMap` 键相等性取代字符串拼接，从根上消除。
