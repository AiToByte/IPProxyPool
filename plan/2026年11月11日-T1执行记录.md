## T1-P1a — ADMIN_ADDR bind before dependency startup

**Problem.** Previously `ADMIN_ADDR` was read late, and the listener was bound in a detached Tokio task. An invalid or occupied address logged an error but allowed the proxy to continue without its Admin control surface. The failure could occur after Redis and background workers had already started.

**Contract.** Admin is required for this gateway process. The configured address must be parsed without echoing user input, then bound exactly once before Redis, workers, or Pingora service registration. The already-bound `TcpListener` is passed to `axum::serve`; no probe-and-rebind window exists. Hostname syntax remains accepted. Default remains `127.0.0.1:9092`; missing and empty settings use the same default. Port 0 is retained for test/ephemeral use.

**RED evidence.** Added child-process test `tests::invalid_admin_addr_aborts_before_redis_setup` and ran:

```text
cargo test --manifest-path gateway/Cargo.toml --locked tests::invalid_admin_addr_aborts_before_redis_setup -- --exact --nocapture
```

Before implementation: failed as intended because the child exited 101 from `redis::Client::open("invalid-redis-url-secret-sentinel")` before reporting `ADMIN_ADDR`; expected exit was 1. This proved the old bootstrap order was wrong.

**Implementation.** Added pure address parsing and unit tests in `gateway/src/startup_config.rs`. `setup_gateway()` now validates and binds the required Admin address before other dependency initialization, and moves the bound listener into the Axum task.

**Behavior evidence.** Tests pass:

- `startup_config::tests::admin_addr_defaults_when_missing_or_empty`
- `startup_config::tests::admin_addr_accepts_socket_hosts_and_preserves_original_host`

- `tests::invalid_admin_addr_aborts_before_redis_setup`

The subprocess tests assert nonzero exit before Redis diagnostics and verify that neither the invalid address sentinel nor the invalid Redis URL is emitted.

**Independent review.** The independent startup review approved the listener parse/bind/handoff and startup order. The security review identified two issues: non-loopback Admin binding exposes the API over plaintext HTTP, and an unset configured Admin key could authenticate an empty supplied header. The latter was reproduced and fixed in this item; the former is documented as a deployment constraint, while the default remains loopback. The focused Rust review found no remaining issue in the empty-key guard. The regression test covers both accepted credential headers with empty and non-empty supplied values.

**Security regression evidence.** Added `admin::tests::empty_configured_admin_key_rejects_empty_credentials` and ran:

```text
cargo test --manifest-path gateway/Cargo.toml --locked empty_configured_admin_key_rejects_empty_credentials -- --nocapture
```

Before the fix, the test failed because an empty `X-Admin-Key` received HTTP 200 while the configured key was empty. The middleware now rejects all requests immediately when its configured key is empty. After the fix, both `X-Admin-Key: ""` and `Authorization: Admin ` return 401.

**Admin exposure contract.** Admin remains plain HTTP. Non-loopback binding is only suitable on a trusted private network, or behind a TLS-terminating proxy with a trusted proxy-to-gateway network. `docs/ADMIN_API.md` and `docs/OPERATION.md` now state the non-empty key and transport constraints. No public-network deployment is claimed safe by this change.

**Rollback.** Revert only the ADMIN_ADDR preflight/parser/test item if the control plane is intentionally reclassified as optional. This would restore the previous partial-startup behavior and is not recommended. The auth hardening should remain; reverting it reopens empty-key authentication. Do not revert neighboring user changes.
