# 生产可信化下一轮实施计划

**建立日期：2026-11-11**  
**轨道：T1 生产可信化**  
**状态：DRAFT / 待事实核对与用户批准**  
**约束：本计划本身不是代码实施授权；开始执行前需逐项确认当前工作树 P0/CONNECT 收口状态。**

## 1. 目标

在不扩大代理协议范围的前提下，形成可复现的单实例生产候选证据：启动配置正确、ready 语义可信、依赖断开与恢复可观察、后台任务可停止、流量和计费可对账、容量与回滚有数据。

本轮验收对象限定为：**现有普通 HTTP 数据面、现有 HTTP/SOCKS 出站、明确配置、Redis/ClickHouse 依赖策略、Linux 生产运行边界**。

## 2. 明确非目标

本轮不做：

- CONNECT 协议扩展、TLS 入站、H2/H3、PAC、CONNECT-UDP/IP/MASQUE；
- 企业 RBAC/OIDC、集群配置发布、跨实例账务设计；
- 替换生产 LinUCB 或引入新路由算法；
- 代理 IP 资源采购、商业 SLA 承诺；
- 顺手重构 unrelated modules；
- 覆盖或清理当前用户已有未提交文件。

当前 CONNECT/P0 只作为冻结输入和前置项，不能因这轮生产可信化计划而重写。若前置尚未完成，先停止本计划的实施阶段，转为记录剩余阻塞和批准新的单项计划。

- `git status --short`、HEAD、工作树文件清单、未跟踪文件清单。
- 当前 P0 实现：Admin 路径脱敏、Tenant 版本化写回、Stream pending 安全、ClickHouse 回放、分片拒绝、零权重保护。
- 当前 CONNECT listener 的绑定限制、认证、字节结算、连接 admission、隧道关闭指标和测试结果。
- `QUALITY_BASELINE.md`、`COVERAGE_BASELINE.md`、`PERF_BASELINE.md`、`SUPPLY_CHAIN.md` 的快照日期和范围。

### 保护原则

- 不 reset/checkout/clean，不覆盖 `repomix-output.xml`。
- 对尚未通过审查和真实端到端验收的工作树能力标为候选实现。
- 所有文件改动只在批准的子项范围内进行；运行 formatter 前确认会影响的文件集合。
- 历史 `plan/` 与 `EXEC_LOG.md` 只追加新证据，不改写旧记录。

## 4. 计划工作项与排序

每项必须单独批准，单独验证。顺序不等于一次批准所有范围。

### T1-P0 当前正确性闭环复核

复核现有未提交 P0 变更是否达到各自行为门，不默认因代码存在或测试数量上升就视为完成：

1. Admin 审计日志覆盖租户 Key、percent-encoding、未知路径、畸形路径和 fallback；
2. Tenant dirty version 只确认对应快照版本，失败/取消/并发改写不清脏；
3. Stream pending 不误删、XAUTOCLAIM 语义明确、跨重启 exactly-once 不作虚假承诺；
4. ClickHouse replay SQL 对齐权威 DDL、毫秒时间戳与 JSONEachRow 通过真实 HTTP stub 契约；
5. REDIS_STREAM_SHARDS 在外部依赖初始化前严格拒绝不支持的值；
6. SLA/自动倍率不复活人为禁用节点。

**门**：逐项标识 RED/GREEN 命令、执行结果和未验证 live 依赖。尚有缺陷则分别开修复子项，不在一个宽泛提交中顺带扩大范围。

### T1-P1 启动配置与降级策略

- 建立配置字段清单：监听、鉴权、Redis、ClickHouse、tenant store、CONNECT（只校验现有选项，不扩协议）、节点文件、限流、GeoIP。
- 对非法值、互斥组合和缺失密钥制定 fail-fast/允许降级的类型化决策表。
- 校验错误服务端可诊断、客户端不泄露 secret；URL 凭据必须脱敏。
- 在创建网络连接、后台 worker 或 listener 前完成纯配置校验。

**RED/GREEN**：表驱动测试覆盖 missing/default/invalid/boundary/conflict；至少一项启动子进程测试证明非法设置在依赖连接前退出且日志不含 secret。

### T1-P2 liveness 与 readiness

- 保留旧 `/api/v1/health` 兼容语义，但明确它不等价于 ready。
- 设计 `/livez`：只反映进程/event loop 活着。
- 设计 `/readyz`：反映相关 listener 绑定成功、配置有效、运行模式所需组件可接流量。
- 依赖降级模式下 ready 的规则按产品契约明确；不能简单要求所有可选依赖必须在线，也不能把“进程已启动”当 ready。
- 状态可区分 starting / ready / degraded / stopping。
- 暴露状态指标和结构化日志，避免高基数标签。

**RED/GREEN**：测试启动中、正常、Redis 降级、ClickHouse 降级、恢复中、listener 关闭和停止中；验证 HTTP 状态与响应字段。

### T1-P3 生命周期、依赖恢复与关停

- 明确 worker supervisor 的错误、panic、backoff 和停止状态语义。
- 停止流程：拒绝新连接 → 广播 shutdown → 停止周期任务 → 在预算内 flush → 关闭 listener/释放资源。
- Redis：分别故障注入断开、恢复、Stream 积压、pending reclaim、重启；确认没有 pending 数据破坏。
- ClickHouse：分别断开、恢复、插入失败、hold-ack、缓冲上限和进程重启。
- 完成 SIGTERM / Ctrl-C / 强杀三类路径；Windows 与 Linux 结果分别记录。

**门**：停机后不 respawn；新请求拒绝；槽位/连接释放；允许的待处理遥测有明确结果；缺少真实依赖时标注 NOT RUN，不以 mock 报通过。

### T1-P4 可观测、对账和运维材料

- 用 trace_id 对齐客户端结果、网关 access log、metrics、Redis Stream 和 ClickHouse row。
- 定义至少一套核心 SLI：请求成功率、429 分流、upstream 502/504、ready 比例、tenant settle 差异、telemetry lag、sink last-success。
- 确认 Prometheus 告警有有效接收路径；没有接收方时不得描述为 paging。
- 增加 runbook：启动失败、依赖降级、连接池耗尽、遥测积压、节点被摘除、配置回滚。

**门**：注入一次可控错误，按 trace_id 完成四方对账；告警能触发并进入已配置接收端，或如实记录“无 paging”。

### T1-P5 容量与发布候选

- 先在 Linux 固定版本/机器上测 ground truth，再测网关。
- 测试矩阵至少包含 telemetry off/on、单/多上游、并发梯度、真实 TLS/SOCKS 上游、CONNECT 关闭/开启但不把 CONNECT 扩展当本阶段目标。
- 分开报告 tenant quota shedding 与代理路径饱和；不改限流器以美化 QPS。
- 记录 CPU、RSS、FD、线程、连接复用、请求/连接成功率、p50/p95/p99/p999、Redis lag、ClickHouse sink lag。
- 预先定义 canary 范围、停止条件和旧 binary/config 回滚步骤。

**门**：结果可从仓库脚本或明确命令复现，吞吐/延迟声明附拓扑、版本、配置和限制；回滚实际演练通过。

## 5. RED/GREEN 与状态门

每个工作项使用统一状态：

```text
DRAFT → FACT-CHECKED → APPROVED → RED-RECORDED
→ IMPLEMENTING → GREEN → REVIEWED → VERIFIED → CLOSED
```

- `DRAFT` / `FACT-CHECKED` 只做取证与设计。
- `APPROVED` 才写第一条测试。
- `RED-RECORDED` 才写实现。
- `GREEN` 后才请求代码/安全审查。
- CRITICAL/HIGH 回到 IMPLEMENTING。
- `VERIFIED` 才更新当前能力文档与质量基线。
- 每项关闭时写明影响路径、RED/GREEN 命令、live/mock 区分、安全审查、回滚方式、文档同步和未验证内容。

计划/证据矩阵的记录格式：

| ID | State | 受影响文件 | RED 证据 | GREEN 证据 | live 证据 | Review | Rollback |
|---|---|---|---|---|---|---|---|
| T1-P1a | RED-RECORDED | `gateway/src/main.rs` | `cargo test --manifest-path gateway/Cargo.toml --locked tests::invalid_admin_addr_aborts_before_redis_setup -- --exact --nocapture`；当前 RED：子进程 exit code 为 101 而非预期 1，因 Redis `Client::open` 先于 ADMIN_ADDR 验证 panic；没有 ADMIN_ADDR 诊断 | 待实现 | 不需要 live Redis；子进程使用无效 Redis URL 验证 ADMIN_ADDR 检查先于 Redis 初始化 | 待 code/security review | 未实现，不改变运行行为 |

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 当前工作树未提交且范围大 | 覆盖、混合基线、误归因 | 每轮计划先列保护清单和 diff 盘点；不清理/重写用户文件。 |
| health 被误当 ready | 流量发往未就绪实例 | 明确状态机与依赖模式；对外测试状态码。 |
| mock 被当 live | 过度宣称恢复能力 | 证据标记 R/T/L/G；live 不可用即 NOT RUN。 |
| 异步计量与多实例 | 丢账/重复计量 | 幂等 settlement event 和账务语义独立设计；本轮不宣称金融账本。 |
| 供应链数据库过期 | 误报安全状态 | 发布时刷新数据库并记录扫描时间、工具版本和结果。 |
| 性能被限流器遮挡 | 误判容量 | 同时报策略 shedding 和代理路径容量；不更改限流器伪造裸性能。 |

## 8. 完成定义

本计划只有在以下条件全部满足时才能标记 CLOSED：

- T1-P0 每项独立关闭或明确列为阻塞且经用户重新确定范围；
- P1 配置与 ready 契约已批准、测试覆盖边界路径；
- P2 真实 Redis/ClickHouse 故障恢复和 Linux 停机证据已留存；
- P3 trace_id 对账、告警接收与 runbook 通过；
- P4 Linux 容量与遥测开销记录完整；
- P5 发布 canary 和回滚演练完成；
- 所有 CRITICAL/HIGH 代码与安全审查发现关闭；
- 受影响文档、配置参考和质量基线与当前证据一致；
- 每个未验证项仍明确标记，未被写成已交付能力。

T1 关闭后，才允许针对 T2 控制面或 T3 协议阶段起草独立的 APPROVED 计划。
