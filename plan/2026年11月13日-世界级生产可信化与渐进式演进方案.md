# 世界级生产可信化与渐进式演进方案

**建立日期：2026-11-13**  
**适用仓库：IPProxyPool**  
**状态：FACT-CHECKED / 等待逐项执行记录**  
**原则：先证据、后能力；先安全阻塞、后生产化；不以 mock/stub 冒充 live；不覆盖当前工作树既有改动。**

## 1. 目标与边界

目标不是堆叠功能，而是把现有代理网关演进为：

- **安全默认**：TLS、鉴权、凭据、SNI、连接池身份和错误边界 fail-closed；
- **可证明可靠**：每个关键交付有可复现 RED/GREEN、真实依赖和平台证据；
- **有界运行**：请求、连接、pending、重试、队列、内存、FD 和遥测都有硬上限；
- **可恢复**：Redis/ClickHouse/上游/worker/进程重启后的行为有明确语义；
- **可运维**：liveness、readiness、degraded、draining、stopping 不混淆；
- **可回滚**：配置、二进制、schema、策略和 canary 都有回退路径；
- **可解释演进**：路由策略、运行健康、管理意图、结算和遥测分别建模。

本方案不承诺当前仓库已经达到全球顶级生产标准。所谓“世界级”在本方案中指：以成熟代理、流处理、数据仓库和可观测性系统的工程约束为参照，建立可以被独立复核的工程闭环。

### 明确非目标

当前 T1 未关闭前不做：

- H2/H3、PAC、CONNECT-UDP/IP/MASQUE、MITM/TLS 解密；
- RBAC/OIDC、跨实例配置发布、集群账务；
- 替换 LinUCB 或引入不可解释黑盒路由；
- 代理 IP 采购、商业 SLA 承诺；
- 为了“世界级”重写 Pingora、Redis 或 ClickHouse。

## 2. 设计借鉴与本项目落点

### 2.1 Envoy 类资源保护，但不照搬 Envoy

借鉴三层边界：

1. **进程过载保护**：内存、FD、活跃请求、连接、隧道、队列达到水位时，提前拒绝昂贵工作；区分容量型 503 与租户配额 429。
2. **上游 circuit breaking**：每 provider/node 分开限制连接、活跃请求、pending 获取、重试和连接池；重试消耗统一 deadline/budget，禁止 retry storm。
3. **readiness/drain**：draining 先变为 not-ready，再停止新 admission，给已有请求/隧道有界完成时间。

### 2.2 Redis Streams 的真实语义

`XAUTOCLAIM` 的 `COUNT` 是扫描/尝试上限，不是“必然返回 N 条”；服务端扫描量还受内部上限约束。返回的 next cursor 必须跨调用保存；`0-0` 只表示本轮扫描完成，后续周期仍要从头扫描以覆盖后来变 stale 的消息。claim 会重置 idle 时间；被 trim/deleted 的消息可能从 PEL 中清除，必须计为可观测的数据损失信号。

本项目当前契约：

- fresh 事件进入 Redis 前可能因有界 channel/drop 和 MAXLEN 被丢弃；
- 已进入 Redis PEL 的事件采用 at-least-once；
- ClickHouse response-loss、进程重启和有限去重窗可能造成重复；
- 不宣称跨重启 exactly-once，除非增加稳定事件身份和仓库级幂等证明。

### 2.3 ClickHouse 的重试边界

ClickHouse insert retry dedup 是有限窗口、设置和表引擎相关的 block 去重，不是无条件 exactly-once。稳定 retry identity、相同 block 切分/内容和足够 dedup window 才能降低重复；response-loss 后成功提交再重试仍可能重复。后续应：

- additive migration 将 `event_id` 写入权威表；
- 为批次保存稳定 manifest/token；
- 区分 telemetry analytics 与租户结算/账务事实；
- 将 duplicate、trim、drop、pending age、last-success 作为指标和对账字段。

### 2.4 OpenTelemetry 语义

统一 trace/metric/log 的 service、version、instance、error.type、duration unit、span kind 和属性命名；现有 `X-Trace-Id` 作为受边界验证的 correlation field，不直接假称为合法 W3C trace ID。禁止把凭据、原始 URL/query、任意 target/domain、tenant ID 放入无界 metric label。

### 2.5 Pingora 的使用策略

保留 Pingora 作为数据面基础：利用其 Rust 异步 I/O、可编程 proxy hooks、连接复用和 listener/service 体系。只在现有边界上增加 typed state、admission、health 和 shutdown 适配，不引入第二套代理运行时。

## 4. 阶段计划

### S0 工作树事实冻结

**交付**

- 记录 HEAD、tracked/untracked、工具链、OS、依赖锁定版本；
- 将当前改动分为 P0、CONNECT、TLS、metrics、docs、CI、replay；
- 保护 `repomix-output.xml` 和用户既有改动；
- 重新生成当前质量数字，不改历史执行记录。

**退出门**

- 任何能力声明都标为 workspace candidate，未把工作树状态写成发布能力；
- 依赖不可用、凭据不可用、Linux 不可用都单独写 NOT RUN/BLOCKED。

### S1 T1-P0-TLS：上游 TLS fail-closed

**范围**

- `gateway/src/gateway/upstream.rs`；
- 对应 gateway TLS 单测；
- 必要的本地 TLS fixture/test helper；
- 相关安全文档。

**行为契约**

- 443 上游必须启用 TLS；
- `verify_cert=true`、`verify_hostname=true` 显式固定；
- 空/空白/控制字符 SNI 直接拒绝；
- 受信 CA 成功，错误 CA、过期证书、错误 SAN、空身份失败；
- SNI 表示 HTTPS proxy hop 的证书身份，而不是盲目使用最终目标域名；
- 不把 `SSL_CERT_FILE`/`SSL_CERT_DIR` 当作关闭校验开关；它们只能提供受信根；
- 失败日志不包含密码、完整 URL 或认证头。

**RED/GREEN**

- RED：当前 TLS flags/SNI 负向测试失败或无法证明；
- GREEN：focused unit + local TLS fixture + strict Clippy/fmt；
- LIVE：真实 HTTPS proxy/错误证书至少各一条；不可用则 BLOCKED。

**回滚**

- 只回滚本切片；不得恢复证书校验 bypass；无法安全验证时禁用受影响 TLS 流量或回到已验证安全二进制。

### S2 T1-P0：ChSink 和仓库落地闭环

**交付**

- 保留 worker-local reclaim cursor；
- 保留成功 insert 后 ACK；
- live fixture：PEL 大于单页、前页 insert fail、后页可达、cursor wrap、恢复后所有 rows 对账；
- 查询 ClickHouse 中本次唯一 provider/event identity；
- 记录 pending count、attempt count、landed count、duplicates、deleted/trimmed IDs、恢复时长；
- 修正 live fixture cleanup 使用的 database/table 配置，不硬编码错误数据库。

**退出门**

- Redis PEL 和 ClickHouse row 按 event_id/stream ID 对账；
- failed insert 不 ACK；
- response-loss/重启重复语义被测试或明确标注；
- 不把 empty PEL 当作“无重复”证明。

**回滚**

- 保留 Redis PEL；不得自动删除有 pending 的 consumer；
- 关闭 live sink 只允许在明确 loss policy 下进行，不能静默丢失。

### S3 T1-P1：typed config 与降级决策

**配置模型**

先覆盖启动关键字段：ADMIN/GATEWAY/METRICS/CONNECT listener、ADMIN_API_KEY、REDIS_URL、CLICKHOUSE URL/credentials/db、TENANT_STORE、REDIS_STREAM_SHARDS、NODES_FILE。后续再纳入 GeoIP/限流/interval。

**决策规则**

- 纯配置解析在任何 network I/O、listener、worker 前完成；
- required：非法或不可用时 fail-fast；
- optional：降级需明确 loss/availability 语义并暴露 reason；
- unknown tenant-store、空 required secret、conflicting TLS/port、invalid URL 不静默 fallback；
- `Debug`/日志不打印 credential-bearing URL。

**测试**

- 表驱动 missing/default/invalid/boundary/conflict；
- 子进程证明非法配置早于 bind/Redis/worker；
- sanitized diagnostics；
- 配置 fingerprint 不含 secret。

### S4 T1-P2：健康、就绪、drain 状态模型

新增最小共享状态模型，状态与能力分离：

```text
Starting → Ready
Starting → Degraded
Ready → Degraded
Ready/Degraded → Draining → Stopped
```

**接口**

- `/livez`：进程/event loop 可响应；不因 ClickHouse 可选故障变 503；
- `/readyz`：实际启用的 listener 可接新工作、配置已验证、required dependency 满足；
- `/api/v1/health`：保留兼容旧语义，文档明确不等价 readiness；
- 详细 reason 受保护或低基数化，不把 secret/tenant/domain 放 label。

**关键规则**

- optional telemetry/warehouse down 可 degraded-ready，取决于 loss policy；
- required tenant store/auth dependency down 必须 unready；
- drain 先 unready，再拒绝新 admission，再有界等待已有工作；
- readiness 不跟随瞬时 overload 抖动，使用 hysteresis。

**测试**

- black-box HTTP 状态/body；
- startup、normal、optional dependency down、required dependency down、recover、listener failure、drain、stop；
- 现有 health 兼容性。

### S5 T1-P3：有界运行、恢复和关停

**有界预算**

- per-tenant concurrency/QPS；
- per-node/provider active requests/connections/pending acquisition；
- retry count、retry deadline、retry budget；
- CONNECT tunnel、body、idle、handshake、shutdown drain；
- telemetry channel、Redis stream、ClickHouse batch、FD/RSS。

**恢复**

- worker supervisor：panic/error/backoff/restart counter/stop-aware；
- Redis reconnect、pending reclaim、trimmed ID、consumer restart；
- ClickHouse retry、response loss、dedup window expiry；
- no post-stop respawn；
- shutdown 顺序：not-ready → reject admission → stop periodic workers → flush bounded work → close listeners。

**证据**

- Linux SIGTERM/Ctrl-C/kill -9；
- Redis/ClickHouse 故障注入和恢复；
- permit/slot/connection/FD/RSS 无泄漏；
- no retry storm；CONNECT 200 后不重试。

### S6 T1-P4：语义可观测和运维材料

**统一事件**

```text
request_id / trace_id / span_id
policy_version / node_id / provider / target class
attempt_id / outcome / error.type / retry ordinal
stream_id / event_id / sink batch id / warehouse row identity
```

- trace/log/Redis/ClickHouse 能按受控 correlation identity 对账；
- metrics label 只用固定集合；
- distinguish request success, attempt success, tunnel lifetime, telemetry loss, sink lag；
- alert receiver 用真实 webhook/test receiver 验证，不把 Prometheus rule 等同 paging；
- runbook：启动失败、TLS 失败、Redis down、CH down、pending 积压、overload、drain、回滚。

### S7 T1-P5：Linux 容量和发布候选

**矩阵**

- telemetry off/on；
- single/multiple upstream；
- HTTP/SOCKS/真实 TLS proxy；
- concurrency gradient、slow client、long tunnel、skewed tenant；
- Redis/ClickHouse healthy/degraded；
- release binary。

**输出**

CPU/RSS/FD/threads、reuse ratio、goodput、p50/p95/p99/p999、429/503 分布、Redis lag、pending age、ClickHouse lag、telemetry drop/loss。明确硬件、拓扑、版本、配置和停止阈值。

**发布门**

- canary 比例、abort 条件、错误预算；
- last known good binary/config；
- schema backward compatibility；
- rollback 实际演练。

## 5. T2/T3/T4 后续方向

### T2 企业控制面

T1 关闭后再做：版本化 `ConfigSnapshot`、checksum、审批、发布、ACK/NACK、漂移检测、secret reference、OIDC/RBAC、rotation、审计、多实例租户 quota ownership。账务从 telemetry analytics 分离，不以周期 Redis flush 直接宣称金融账本。

### T3 协议批次

HTTP/1.1 CONNECT 先完成真实标准客户端、TLS/SOCKS 上游、framing、半关闭、no-retry-after-200、drain 证据；TLS 入站、H2/H3、PAC、CONNECT-UDP/IP 各自独立计划，不因 CONNECT 基础实现存在而自动宣称支持。

### T4 路由 2.0

先补 decision/attempt schema、候选集摘要、propensity、holdout/shadow、策略版本和回放；再做 constrained policy、canary 和 rollback。当前 LinUCB 不在 T1 改写。

## 7. 全局退出条件

不得把本路线标为 CLOSED，除非：

- P0 每项独立有 RED/GREEN 和 live/mock 区分；
- TLS 负向证书测试、ChSink PEL/ClickHouse 对账通过；
- typed config、livez/readyz、drain、依赖恢复和 Linux lifecycle 已验证；
- alert receiver、runbook、容量、canary、rollback 有真实证据；
- 所有 HIGH/CRITICAL review finding 关闭；
- 文档/质量基线/能力声明与证据同步。

## 8. 参考原则

- Envoy：过载管理、上游 circuit breaking、健康检查与 readiness/drain 的分层设计；
- Redis Streams：XAUTOCLAIM cursor、COUNT 扫描边界、idle reset、trim/deleted ID；
- ClickHouse：有限窗口 block dedup，response-loss 后不可无条件宣称 exactly-once；
- OpenTelemetry：统一资源、span、metric、log 语义与受控 correlation identity；
- Pingora：保留 Rust 异步代理核心，增加本项目状态、预算和生命周期适配。
