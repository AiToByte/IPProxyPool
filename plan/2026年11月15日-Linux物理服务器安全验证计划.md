# IPProxyPool Linux 物理服务器安全验证计划

**建立日期：2026-11-15**  
**范围：T1 生产可信化的 Linux / 真实依赖验证准备与执行方案**  
**状态：DRAFT / 待服务器安全接入确认及逐阶段执行**  
**目标环境：用户提供的 WireGuard 可达 Linux 物理服务器；具体 OS、资源、现有服务和容量尚未核实**  
**安全原则：先只读盘点，后隔离测试；不停止、不重启、不覆盖现有服务；不把凭据写入仓库、命令行、日志或报告。**

---

## 1. 目标

在用户提供的 Linux 物理服务器上，为当前 IPProxyPool 分支建立可复核的 T1 证据，补齐 Windows 开发环境不能替代的 Linux 行为验证：

- 核实服务器是否满足测试资源要求，记录 OS、内核、CPU、内存、磁盘、文件系统、容器运行时和已有负载；
- 在不干扰现有业务的前提下，验证当前已推送 commit 的 Linux release 构建和启动行为；
- 验证 `/livez`、`/readyz`、Redis 必需/可选策略、listener 探测和 shutdown readiness withdrawal；
- 在**隔离的 IPProxyPool 测试实例及其专属依赖**中运行 Redis/ClickHouse live 故障与恢复测试；
- 为 SIGTERM、进程强杀、恢复、遥测对账、容量和回滚提供清晰的分阶段证据；
- 将真实结果追加到 `EXEC_LOG.md`，并在证据充分后更新当前质量/能力基线。

本计划本身不代表允许停止、重启、删除或覆盖服务器上的任何现存服务。每个阶段的退出条件和允许操作见后文。

## 3. 服务器规格建议

| 档位 | CPU | 内存 | 系统盘/数据盘 | 适用范围 |
|---|---:|---:|---:|---|
| 最低集成验证 | 4 vCPU | 8 GB | 60 GB SSD | release build、基础 HTTP、Redis/ClickHouse smoke；不跑完整观测栈与高并发压测 |
| **推荐 T1 验证** | **8 vCPU** | **16 GB** | **100 GB NVMe 可用空间** | readiness、真实 Redis/ClickHouse 故障恢复、shutdown/restart、遥测对账及中等压测 |
| 容量专项 | 16 vCPU | 32 GB | 100 GB 以上 NVMe | telemetry on/off、并发阶梯、资源水位；尽量使用无其他业务负载的独占主机 |

### 3.1 软件与网络

- 优先 Ubuntu Server 24.04 LTS 或 Debian 12，x86_64；记录实际发行版、内核、glibc、Rust 工具链版本。
- Docker Engine + Docker Compose plugin；仅在服务器已有 Docker 且用户允许使用时采用容器依赖。
- SSH 只通过已验证的 WireGuard 地址访问；管理端口限制在 WireGuard/本机回环。
- 需要可用的 Rust crates 缓存或受控出站网络；如果不能下载依赖，记录为构建阻塞，不改变服务器网络或代理配置。
- 不要求向公网开放任何端口；不允许将 Redis、ClickHouse、Admin、metrics、Prometheus、Grafana 暴露到公网。

### 3.2 资源预算

以下为推荐 8 vCPU / 16 GB 测试机上的初始上限，执行前仍需先检查主机现状：

| 组件 | 建议内存上限 | CPU 限制 | 默认是否启动 |
|---|---:|---:|---|
| Gateway release 实例 | 2 GB | 2 vCPU | 是，测试阶段明确启用时 |
| Redis 测试实例 | 512 MB | 1 vCPU | 仅 Redis/live 测试阶段 |
| ClickHouse 测试实例 | 4 GB | 2 vCPU | 仅 ClickHouse/live 测试阶段 |
| Prometheus/Grafana/Alertmanager | 合计 2 GB | 合计 1 vCPU | 否；仅 SLI/告警测试阶段 |
| 预留给 OS、SSH、现有服务及 page cache | 至少 6 GB | 至少 2 vCPU 余量 | 始终保留 |

若盘点发现现有业务的 CPU、内存、磁盘 I/O 已接近饱和，或测试会把可用内存降到 6 GB 以下，则停止，不启动依赖和压测；改为安排维护窗口或提供隔离测试机。

## 5. 阶段 0：安全接入与只读主机盘点

### 5.1 接入前提

- 先轮换聊天中暴露的 root 密码；不在仓库或日志存储新凭据。
- 建议创建专用、短期测试账号；若需 root 执行 Docker，再逐项确认必要权限，不默认授权长期 root 登录。
- 通过 SSH host-key fingerprint 确认目标确属用户服务器；不得用 `StrictHostKeyChecking=no` 绕过身份确认。
- SSH 建立后先运行只读盘点，且不创建目录、不安装软件、不启动容器。

### 5.2 只读采集项

- OS 发行版、kernel、架构、时区、uptime/load average；
- CPU 型号、逻辑核、NUMA；内存和 swap；
- `df -hT`、inode、挂载点、磁盘型号/类型、剩余空间；
- 当前监听 TCP/UDP 端口、systemd 服务、用户进程、容器和 Compose project；
- Docker/Compose 版本、容器状态、容器资源占用；
- 是否存在既有 IPProxyPool 进程、容器、目录、systemd unit、数据卷；
- WireGuard interface/route 状态只读检查，不更改 peer、route、防火墙或 MTU；
- 相关目录权限与仓库 HEAD，不读取或输出现有 secret 文件内容。

### 5.3 阶段门

只有满足以下条件才继续：

- host-key fingerprint 与用户确认相符；
- 主机资源达到用户选定的验证档位；
- 现有 IPProxyPool 服务、依赖容器、进程和卷已识别；
- Docker 是否可用于隔离实例、测试端口是否可用、磁盘空间是否足够均明确；
- 当前服务没有高负载、磁盘空间告警或不明进程风险。

若发现正在运行的项目服务或依赖：默认视为**不可触碰**。禁止将 live 故障注入指向这些进程或容器。

## 6. 阶段 1：测试工作区和依赖隔离

### 6.1 代码版本

- 只测试明确的已推送 commit，首选 `5ba7ae3` 或更新且已完成本地验证的 commit。
- 在独立验证目录 checkout 精确 commit；不得在服务器现有部署目录执行 `git pull`、覆盖文件或切换正在运行的工作树。
- 在服务器记录 `git rev-parse HEAD`、dirty status 和构建参数。
- 如需复制源码，采用独立、版本化目录；不复制 `.env`、`data/nodes.json`、代理列表、repomix 输出、用户记忆或旧日志。

### 6.2 端口与容器隔离

仓库 `docker-compose.yml` 含固定 `container_name`（如 `ipproxy-redis`、`ipproxy-clickhouse`）、默认端口和持久卷，不适合未经检查直接在已有环境重复 `compose up`。按以下规则隔离：

1. 先检查默认端口 `6379/8123/9010/9090/9091/9092/9093/8916/8917` 和固定容器名是否已占用；只读检查不代表允许覆盖。
2. 若默认资源被占用，不得停止、重命名或重建现有服务；为测试创建独立 Compose 文件/覆盖配置，使用唯一 project 名、唯一容器名、非冲突 loopback 高端口和独立命名卷。
3. 新 Redis/ClickHouse 容器必须设置显式内存/CPU 限制、测试专属卷、无 `container_name` 冲突；测试服务仅绑定 `127.0.0.1` 或 WireGuard 内部接口（默认只回环）。
4. Gateway 配置对应测试 Redis/ClickHouse URL 和本地上游；不得指向现有生产依赖。
5. 每个测试容器启动前保存其 project 名、container ID、卷名和端口映射；任何 cleanup 只允许针对本计划创建且 ID 核对一致的对象。

### 6.3 禁止操作

整个验证周期禁止：

- `docker compose down` 不带明确测试 project；禁止 `docker system prune`、`docker volume prune`；
- `killall`、按宽泛进程名 `pkill`、`systemctl restart/stop` 未确认的服务；
- `rm -rf`、覆盖/迁移现有数据目录、重置 Redis/ClickHouse 数据卷；
- 改 SSH、防火墙、路由、WireGuard、sysctl、内核参数；
- 对生产 Redis/ClickHouse 执行 FLUSH、DROP、清空 stream/table 或破坏性故障注入；
- 压测非 IPProxyPool 测试目标，或向公网/未授权上游发流量。

## 8. 阶段 3：Linux 启动、liveness 与 readiness

### 测试拓扑

- Gateway 使用独立测试配置、独立监听端口、独立 Admin/metrics 端口；
- 首轮以普通 HTTP 代理 listener 为 required listener；本阶段不把可选 CONNECT 纳入 ready 判定；
- 上游使用本机 loopback mock，仅对项目测试流量提供 HTTP/SOCKS 行为；
- readiness GET 请求低频轮询，不作为压测流量。

### 验收矩阵

1. 错误地址/非法 typed config：进程按设计启动失败，固定字段错误，不泄露 secret，不触碰外部依赖；
2. Admin listener bind 失败：在 Redis/worker/Pingora 初始化前退出；
3. Gateway listener 尚未 ready：`/livez` 可 200，`/readyz` 必须 503；
4. Gateway listener 成功接受本地 TCP probe：`/readyz` 变为 200；
5. listener 后续停止/连接拒绝：周期 probe 在规定窗口内撤回 ready；
6. `TENANT_STORE=memory` 且 Redis 不可用：phase 为 `degraded`，ready 仍为 true；
7. `TENANT_STORE=redis` 且 Redis 不可用：phase 为 `degraded`，ready 为 false；
8. SIGTERM/CTRL-C 到达：`/readyz` 立即转 503；`/livez` 在 server 完全退出前仍只表示 HTTP event loop 活着；
9. `/api/v1/health` 继续需要 Admin Key，返回旧 body，不能把它作为 readiness 使用；
10. 未认证 `/livez` 与 `/readyz` 的 audit 只记录固定 path/status，不含 secret、URL、动态依赖错误。

### 阶段门

- 所有探针状态在服务器端可复现并保存 HTTP 状态/body、时间戳和服务日志；
- 在约定时间内做不到的 transition 写 `NOT RUN/BLOCKED`；
- 不声称这已实现完整 request admission drain。

## 9. 阶段 4：隔离 Redis/ClickHouse live 恢复

### 4.1 健康态基线

- 使用专属测试 Redis/ClickHouse；记录 image tag、server version、资源限制、schema 和独立卷；
- 记录 Gateway 启动配置的 secret 名称与是否设置，不记录 secret 值；
- 写入少量可识别的测试 telemetry/event IDs，记录起始时间和预期数量；
- 验证 Redis PING observer、`/readyz` 初始状态、sink last-success、stream length/PEL 和 ClickHouse row identity。

### 4.2 Redis 故障与恢复

只允许停止/隔离**本计划创建且 ID 已核对**的测试 Redis 容器；不得影响已有 Redis：

- Redis memory mode：Redis down 后 expected `/readyz=200, phase=degraded`；PING 恢复后回 `ready`；
- Redis tenant-store mode：Redis down 后 expected `/readyz=503`；恢复后按 PING 周期回 ready；
- 核实 failure detection 最大时延接近 `probe interval + timeout` 加调度裕量；恢复需一个成功 probe；
- 检查 telemetry drops、stream lag、worker restart、是否发生重试风暴；
- 检查 Redis PEL、consumer group、cursor、pending age；确认测试前后没有清除无关数据。

### 4.3 ClickHouse 故障与恢复

- 只操作隔离 ClickHouse 测试容器；不把 ClickHouse 配置为 readiness required，除非项目 policy 另行批准；
- 故障期间记录 sink error、hold/ack 语义、内存上限、stream lag 和 pending；
- 恢复后对 event ID/row identity 计数，记录丢失/重复/延迟；
- 单独评估 response-loss 和跨进程重启重复；不以 PEL 清空等同无重复；
- 不执行 DROP DATABASE、TRUNCATE、清理测试卷前，确认其为本计划创建的隔离数据。

### 4.4 验收

每次故障测试必须有：注入开始/结束、测试 container ID、Gateway PID、状态码切换时间、恢复时间、PEL/stream/warehouse 前后计数、错误率、drops、duplicates 和结论。无证据项目标 `NOT RUN`。

## 10. 阶段 5：生命周期与关停验证

按风险逐步执行，单次只测试一个项目实例：

1. SIGTERM：确认 readiness withdrawal，停止周期 observer/worker，bounded flush，进程按配置期限退出；
2. Ctrl-C：确认与 SIGTERM 的语义一致或如实记录差别；
3. 强杀测试：只对当前测试 PID 精确发送信号，不按进程名批量杀；记录 Redis/CH 可恢复与不可恢复状态；
4. 重启：确认测试节点配置、tenant store 语义、consumer group、pending reclaim 和 event 重复边界；
5. listener 关闭/端口冲突：只在测试配置和测试端口上演练；
6. 观测终止后是否仍有 Gateway 子进程、observer、连接、FD 或资源泄漏。

**注意**：强杀/故障注入会中断测试中的 IPProxyPool 请求和专属依赖。每次执行前需确认目标 PID/container 是当前计划创建的测试对象；不得对用户现有业务服务执行。

## 11. 阶段 6：Linux 容量基线

只有前面的功能、依赖恢复和生命周期门通过，且服务器有独占余量才开展。

### 测试矩阵

- `cargo build --release` binary；固定 CPU affinity 与机器功耗/云主机类型；记录 kernel 和 Rust 版本；
- 同一测试拓扑先跑客户端→mock upstream 地板，再跑客户端→Gateway→mock upstream；
- 并发梯度：1、4、16、32、64；如余量足够再考虑 128/256，不把并发无上限扩展；
- telemetry off / Redis telemetry on / Redis+ClickHouse sink on 三组；
- 正常请求、慢上游、连接失败、受限租户 429 分开报告；不混算成功 QPS；
- 记录 p50/p95/p99/p999、goodput、status distribution、CPU、RSS、FD、线程、连接复用、Redis lag、ClickHouse lag、telemetry drops；
- 每档运行窗口默认 60 秒，先 smoke 10 秒；有明显负载影响或资源水位告警即停止。

### 硬停止条件

满足任一项立即结束当前测试负载（只结束测试客户端/Gateway test process）：

- CPU 连续 2 分钟超过 80% 且服务器存在其他业务负载；
- 系统可用内存低于 6 GB 或持续 swap-in/out；
- 磁盘可用空间低于 20 GB，或 ClickHouse/系统盘出现 I/O wait 明显饱和；
- 现有非 IPProxyPool 服务的错误率/延迟明显增加；
- 测试流量意外流向公网、未知上游或生产代理节点；
- 无法确认被停止/探测的 PID、container ID、port owner 属于测试实例。

压测结果不作为生产 SLA；只记录此机器、此版本和此拓扑的证据，不能以限流器整形的 429 误判为代理路径失败。

## 12. 阶段 7：回滚、清理与证据留存

### 回滚原则

- 回滚仅作用于本计划创建的 checkout、测试 Gateway 进程和测试 Compose project；
- 不用 `docker compose down` 操作已有 project，不删命名卷，不清理全局镜像/缓存；
- 每个测试容器按 container ID 核对后单独停止；如测试数据需保留供复核则先不删卷；
- 服务器原有服务、配置和卷不做 cleanup；
- 若命令目标无法精确识别则停下并请求用户确认。

### 证据文件

- 仓库只保存不含 secret 的摘要、命令模板、版本和结果；
- 服务器敏感原始日志留在受限的测试目录，不复制回 Git；
- `EXEC_LOG.md` 追加：commit、OS/kernel、资源档位、Docker 与依赖版本、测试拓扑、故障时刻、恢复时间、对账结果、退出码、review 和未验证边界；
- 不提交密码、private key、`.env`、`data/nodes.json`、真实代理快照和原始凭据日志。

## 13. 执行先决条件与审批点

本计划是可执行蓝图，不代表所有阶段一次性获准。开始访问服务器前必须：

1. 轮换聊天中暴露的 root 密码；
2. 通过独立安全渠道确认 SSH host-key fingerprint；
3. 配置临时 SSH key 或受限账号，让当前 runner 可非交互访问；
4. 只读盘点并将主机信息写入本计划的执行记录；
5. 用户确认阶段 1 的隔离测试项目/目录/端口及是否允许创建专属 Redis/ClickHouse 容器；
6. 单独确认是否进入会停止测试容器或执行强杀的故障注入阶段；
7. 单独确认是否进入容量压测阶段及并发上限。

若 SSH 凭据无法建立、host identity 未确认、现有服务边界不明确、资源余量不足或测试端口冲突未解决，状态停留在 `BLOCKED`，不得以密码重试、关闭 host-key 检查或扩大权限的方式绕过。
