## 关键设计决策（先定口径，再动手）

### 决策 1：CH 排序键——为什么只能重建表，不能 ALTER

**现状（已实证）**：`SHOW CREATE TABLE proxy.proxy_telemetry_log` 返回

```sql
ORDER BY (target_domain, provider, status_code, event_time)
```

**唯一查询模式**（`analytics.rs:88-91`）：

```sql
WHERE provider = ? AND country = ? AND event_time >= now64(3) - INTERVAL 5 MINUTE
```

三处错位：

1. `target_domain` 排在第 1 位却**不在任何 WHERE 里** → 主键索引零剪枝；
2. `provider` 虽在第 2 位，但只有前缀被约束时才生效；
3. `country` **根本不在排序键里**。

⇒ 每次 SLA 查询退化为**分区全扫描**。而 `vendor_arbitrage` 每分钟并发 9 次（`docs/FEATURES.md`），随 90 天 TTL 累积线性劣化。

**为何不能原地改：** ClickHouse 的 `ORDER BY` 是**物理存储顺序**，写在 `CREATE TABLE` 里，**不支持 `ALTER TABLE ... MODIFY ORDER BY`**（`MODIFY ORDER BY` 仅在部分引擎下语义受限，MergeTree 不可用）。唯一途径是 `OPTIMIZE TABLE ... FINAL` 重建——**且这会重写全部分区**。

**修法口径：**

- 提供 `deploy/clickhouse/002_reorder.sql`：`CREATE TABLE ..._v2`（新排序键）→ `INSERT SELECT` 搬数据 → `RENAME TABLE` 原子换名 → 旧表 `DROP`（**保留期可选**）。
- 新排序键 `(provider, country, event_time)`：与唯一查询完全对齐，前两列都是 `LowCardinality` 且基数极低（provider ≤ 数十、country ≤ 数百），第三列时间。
- **去掉 `status_code`**：它有 ~600 个取值，夹在时间列之前会把同一时间窗的数据打散到 600 个排序组，破坏时间局部性——而 SLA 查询用的是 `countIf(status_code ...)`（聚合而非过滤），**不需要它进排序键**。
- `target_domain` 降为普通列（若将来有按域查询需求，再靠下面的跳过索引）。

### 决策 2：跳过索引——为什么 `set()` 而不是 `minmax`/`bloom_filter`

`provider`（数十个取值）与 `country`（数百个取值）都是**低基数字典**，`set(N)` 索引直接存取值集合，查询时若 `provider='mock-a'` 不在集合内可整 granule 跳过。`minmax` 对它们无效（min/max 覆盖全值域）。`bloom_filter` 是给高基数数值/字符串列用的，这里用不上。

索引不放进排序键的原因：排序键变了就已重排数据，再叠索引会增加写放大；而 SLA 查询是**每分钟 9 次的高频查询**，索引收益远大于成本。

### 决策 3：告警规则——逐条按 PromQL 语义修正，不做「看起来更合理」的改写

**已实证的两个语义 bug：**

1. **`TelemetryStreamLagGrowing`（`rules.yml:62`）**：
   `increase(redis_stream_length[10m]) > 0`——① `increase()` 语义上只适用于 counter，对 gauge 求「增量」是无效的；② 阈值 `> 0` 意味着只要有正常遥测流量（stream 在增长），表达式恒为真，`for: 10m` 后**永久 firing**。summary 写的是「积压持续增长」，但表达式只能表达「有过增长」。
   **修法：** 改用 `delta()`（gauge 的正确算子）＋ 阈值改为「消费组 lag 超过 N 条」，并用 `redis_stream_length` 与 group 读数的关系给出可操作的阈值。

2. **`SupervisorRestarted`（`rules.yml:40`）**：
   `increase(supervisor_restarts_total[15m]) > 3` **无 `sum by (worker)`**，而 annotation 用 `$labels.worker`（`:45`）——4 个 worker 各重启 1 次（共 4 次）不触发（4 > 3 为假……实际 4>3 为真，但**单 worker 3 次**才恰好触发，**4 个 worker 各 1 次共 4 次**也触发；真正的问题是**无法定位是哪个 worker**——`$labels.worker` 在聚合后消失，annotation 会渲染成空）。
   **修法：** 加 `sum by (worker)`，使阈值语义变为「单 worker 在窗口内重启 >3 次」。

3. **`FreePoolDry30m`（`rules.yml:28`）**：`free_pool_nodes_total` 在 `FREE_ENABLED=0`（缺省）时**恒为 0** → 缺省配置下**永久 firing**。
   **修法：** 加 `and on() (free_pool_enabled == 1)` 之类的启用态门槛——但当前 metrics 未渲染 `free_pool_enabled` 序列。本轮**新增该 gauge**（见 R7-D），使规则可判别。

### 决策 4：直方图桶——为什么必须扩到 30s

`metrics.rs:14` 的 `DURATION_BUCKETS_MS = [1, 5, 10, 25, 50, 100, 250, 500, 1000, 2500]`，桶顶 2500ms。而网关 peer 超时预算是 **1500/5000/3000ms**（`gateway.rs:184-186`），加上重试（失败集上限 16），单请求耗时经常超过 2500ms。>2500ms 的观测全落进 `+Inf`，`histogram_quantile(0.99, ...)` 在 >1% 样本超 2500ms 时在 `le=2500` 与 `+Inf` 之间外推，返回无意义值——**慢的时候 P99 显示得好看**，是最坏的失败方向。

`metrics.rs:371` 已有 60s 截断语义，故桶扩到 `[…, 5000, 10000, 30000, 60000]` 与既有截断一致。

### 决策 5：`.ps1` BOM——为什么改 `.gitattributes` 而不是加 CI 断言

工作区 6 个 `.ps1` 全部带 UTF-8 BOM（PS 5.1 解析中文注释必需），但 `.gitattributes` 的 `* text=auto` 在入库时**剥掉了 BOM**。项目花大力气记录的 PS 5.1 解析故障修复（`ipp_watchdog.ps1:70-72`、`docs/FREE_BASELINE.md:32`）**只存在于这台机器**，任何 clone 都会复现。

两种修法：① `.gitattributes` 加 `*.ps1 text eol=crlf working-tree-encoding=UTF-8`；② 加 CI 断言检查 BOM。**本轮两者都做**——① 是根治（让正确字节入库），② 是防回归（万一有人改坏 attributes 仍能挡住）。

## 执行后的增补说明（诚实记录，含一次被实测证伪的设计）

1. **D1 的 `.gitattributes` 方案被实测证伪（重要）**：
   方案原写「`*.ps1 text eol=crlf working-tree-encoding=UTF-8` 可让 BOM 入库」。实测（git 2.52 / Windows / `core.autocrlf=true`）**五种组合全部失败**：
   `text eol=crlf` / `-text`+`binary` / `working-tree-encoding=UTF-8` / `core.autocrlf=false`+`-text` / `git hash-object --no-filters` —— 产出的 blob 首 3 字节**一律是 `3C 23 52`（无 BOM）**。
   ⇒ BOM 剥离是 git 的**内建行为**，不受任何 attribute 控制。
   **处置：** 移除无效配置（避免后人照抄一个「以为修好了」的假方案），改为
   ① `tools/check_ps1_bom.py` CI 断言守住工作区副本（双向验证通过）、
   ② `.gitattributes` 里**留下完整实测记录表**供后人参考、
   ③ 如实登记根本解法（.ps1 注释改 ASCII / 强制 PS7）**本轮未采纳**的理由。
2. **B2 修掉一处我自己引入的 PromQL 错误**：`ProviderForbiddenRatioHigh` 初版用
   `sum by (provider)(rate(proxy_requests_total[10m]))` 作分母，但
   `proxy_requests_total` **只有 status 标签、没有 provider 标签**（实测 `metrics.rs:404-416`），
   标签集不匹配会导致结果错配。已改为全局分母 + 阈值下调到 5%，
   并在注释中**如实标注该限制**与「将来加 provider 标签后应如何改」。
   这正是「指标名逐个核对」的价值——名字对但标签集错，YAML 语法门同样抓不到。
3. **B1 的修法与原计划略有出入（如实说明）**：原计划写「`increase()`→`delta()`」。
   实际改用 `max_over_time(...[10m]) > 1000`——因为判「积压过大」的语义下，
   绝对长度比「增量」更直接可读，且 `delta()` 仍需另设阈值。
4. **A1/A2 用真实数据量化了收益**：在临时库灌 5 万行后 `EXPLAIN indexes=1` 实测——
   旧排序键 `PrimaryKey Granules: 5/5`（**零剪枝**）vs 新排序键 `Granules: 1/5`
   （**剪掉 80%**）。迁移全流程（CREATE→INSERT→RENAME→对账 50000=50000）已跑通，
   **生产表未触碰**，临时库已 DROP。
5. **C1 顺带修了一个更隐蔽的启动期误判**：除换探针外还加了 `start_period: 20s`——
   CH 冷启动需 10~20s，此前无 start_period 时启动期探针失败会累积 retries
   并被判定 unhealthy（这正是「长期 unhealthy」的部分成因）。
6. **发现并修复一处 CI 跨平台脆弱点（本轮新增，不在原计划）**：
   `ci.yml` 的三条 Python 检查用 `open(path)` 无编码参数，依赖系统 locale 编码。
   本机（GBK）实测三条**全部抛 UnicodeDecodeError**——仓库 YAML/JSON 均含中文注释。
   已统一加 `encoding="utf-8"`，使检查与 locale 无关。CI 跑在 Ubuntu 上本来不会暴露，
   属「本机跑 CI 检查时才发现」的真实脆弱点。

   印证了审阅中「Linux 上 `host.docker.internal` 不可解析导致永久 firing」的判断
