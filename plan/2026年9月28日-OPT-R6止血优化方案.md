## 关键设计决策（先定口径，再动手）

### 决策 1：free 凭据护栏——为什么必须从「请求侧」移到「节点侧」

**现状（缺陷本体）：** `gateway.rs:96-102`

```rust
pub fn free_tier_with_credentials(tier: Option<&str>, has_authorization: bool, has_cookie: bool) -> bool {
    tier == Some("free") && (has_authorization || has_cookie)
}
```

调用点在 `request_filter`（`gateway.rs:539-546`），此时**尚未选路**。而 `router.rs:222-237` 的选路在**无 tier 约束**（`spec.tier == None`）时按权重命中节点，**完全可能命中 free 节点**（`router.rs:171` 的 `matches` 对 `spec.tier` 为 `None` 时直接跳过 tier 检查）。

⇒ 攻击路径：客户端带 `Authorization: Bearer <token>` 或 `Cookie`，但**不发** `X-Proxy-Tier` 头 → 护栏返回 false → 后续选路命中匿名免费节点 → 凭据经陌生出口泄露给第三方。

**修复口径：** 护栏判定输入从「请求声明的 tier」改为「**本次实际选中的节点档位**」。

- 时机：移到 `upstream_peer` 选路**之后**、出站**之前**。
- 命中免费节点且请求带凭据头 → 记审计 + 拒绝（`respond_error(403)`）。
- 粘滞路径与新鲜选路**共用**同一校验（避免两处实现漂移——现有 `router.rs:171` 的 `matches` 与 `:275-296` 的粘滞复核已是两份实现，本项不再增加第三份）。
- **保持存量语义**：`spec.tier == Some("free")` 的显式请求仍被拒（提前拒绝，省一次选路）；`Some("res"/"dc"/None)` 且实际命中付费节点 → 零变化。

**为什么不只补「tier 为 None 时也检查」：** 那样会把「声明非 free 但恰好命中 free 节点」这类偶然命中放行——选路是加权随机的，攻击者无法控制命中结果，但也不能靠「声明 res 就一定走付费」来自证安全。**按实际节点判定才是唯一正确口径。**

### 决策 2：淘汰计数下溢——为什么 `saturating_sub` 是正解而非重试

**现状（缺陷本体）：** `router.rs:144-155`

```rust
let sessions_before = self.session_store.len();      // 145
self.session_store.retain(...);                      // 147  ← 此间数据面可并发 insert(router.rs:322)
let sessions_removed = sessions_before - self.session_store.len();  // 150 ← 插入则下溢
```

`session_store` 被数据面 `select_node_excluding`（`router.rs:322`）并发 `insert`。两次 `len()` 之间若有插入：`before < after` → `usize` 下溢 → debug 下 **panic**，release 下回绕成天文数字（指标失真、后续任何按此计数的逻辑全错）。

同类三处：`router.rs:150/155`、`socks_bridge.rs:274`、`prober.rs:113`。

**放大风险：** `sweep` 任务当前是**裸 `tokio::spawn`**（`main.rs:652`），**无 supervisor**。debug 下这次 panic 会静默杀死整个 sweep 循环（JoinHandle 被丢弃、无日志、无指标），此后会话表/隔离表**无界增长直至 OOM**。

**修复口径：**

1. 三处一律改 `saturating_sub`（语义：并发增长时返回 0，即「本轮净删除为 0」，符合「返回删除个数」的本意，不会掩盖真实删除——真实删除场景下 `after < before`，`saturating_sub` 与 `-` 等价）。
2. 抽出**共享 janitor 计数助手**（`fn removed_count(before: usize, after: usize) -> usize`），三处复用，注释写明为何不能裸减。消除「三份复制」隐患。
3. sweep / prober 等 4 条裸 spawn 全部包进 `supervise_until`（见决策 3），使 panic 不再等于功能永久静默死亡。

### 决策 3：supervisor 覆盖——复用既有 `supervise_until`，零新机制

`main.rs:123-160` 的 `supervise_until` 已具备：stop 感知、指数退避（1s→60s）、跑满 60s 复位、`supervisor_restarts_total{worker}` 计数。本项**只做覆盖补齐**，不改造 supervisor 本身。

**现状 4 条裸 spawn：** `main.rs:318`（prewarmer）、`:417`（telemetry）、`:488`（prober）、`:652`（sweep）。

**边界（必须遵守）：** `supervise_until` 的 `make: Fn() -> Fut` 需可重复调用，故须把「每轮新建的 Client 缓存 / Semaphore」下沉到闭包**内部**（prober 当前在循环外 `Arc::new(CanaryProber)`，须移入）。telemetry 的 `rx_opt.take()` 是**一次性**的 `Receiver`（非 `Clone`），不能直接重入——按「panic 即重启」的原意，telemetry 改为：worker 正常退出/崩溃时**记指标 + 停止重试**（`Receiver` 已耗尽，重启无意义），即用一个显式的「有尽监督」包装，避免假装能重启。**该差异在代码注释中写明，不静默降级。**

### 决策 4：live 门禁——为什么它「结构性不可能通过」

`.github/workflows/live.yml:22-28` 声明 ClickHouse service，但**不挂载 `deploy/clickhouse/001_schema.sql`**。全仓 Rust 源码**无任何 `CREATE TABLE`**（表只由 compose 的 `docker-entrypoint-initdb.d` 创建）。⇒ `ch_sink.rs:598` 的 `assert_eq!(landed, 1)` 必失败（按设计 hold ack）。

叠加：`live.yml:3` 宣称「fails on any SKIP line」，但 `:35-36` **无任何 SKIP 断言**；而 `ch_sink.rs:526/538/551` 三处 `eprintln!("SKIP ..."); return;` ⇒ **依赖全挂也报绿**。

**修复口径：** ① CH service 挂 schema（`options: -v ${{ github.workspace }}/deploy/clickhouse/001_schema.sql:/docker-entrypoint-initdb.d/...`）② 加 SKIP 断言门（`cargo test` 输出 pipe 到 tee，再 `grep -q '^SKIP'` 则非零退出）③ CH service 补 healthcheck（当前无，redis 有；CH 就绪慢 ⇒ 天然 flaky）。
