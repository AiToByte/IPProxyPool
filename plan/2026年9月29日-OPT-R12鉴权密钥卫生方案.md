# OPT-R12 方案：鉴权密钥卫生（`default_key` 策略）—— 零行为变更的加固

> **主体来源:** OPT-R11 深审 Top5 之 5（`default_key` 明文硬编码 ＋ 配额 10000/10000 ＋ 单个 env 开关即可全量关闭鉴权），用户指定为 OPT-R12 主体。
> **附带项:** R11 回归中暴露的 LinUCB 探索退化（见 §6）。
> **铁律（本方案的核心约束）:** **存量行为零变化**。`default_key` 是本仓全部 SDK／脚本／文档的既有约定，改默认值会让存量部署**升级即挂**——那比现状更糟。因此本轮做的是**让危险配置响亮失败**，而不是**让危险配置消失**。

---

## 0. 风险已实测（不靠推断）

用 release 二进制实测 `REQUIRE_API_KEY=0` 的真实行为（mocks 8888/8889/8890 在线）：

| 请求 | 实测 | 含义 |
| ---- | ---- | ---- |
| **完全不带 `X-API-Key`** | **200** ＋ body `mock-b` | **无头请求拿到满额代理服务** |
| `X-API-Key: totally-bogus` | 403 | 路径本身正确 |

机制（已核实 `gateway.rs` `request_filter`）：

1. `should_reject_missing_api_key(require_api_key, has_header)` —— 门关时无头即 403；
2. 门关时 `let api_key = api_key_header.unwrap_or_else(|| DEFAULT_API_KEY.to_string());`
   ⇒ **无头请求被静默补成 `default_key`**，进 `TenantManager` 走**正常配额鉴权**；
3. `main.rs` 启动即 `register_tenant("default", DEFAULT_API_KEY, 10_000, 10_000, burst_for_qps(10_000))`。

**所以「关闭鉴权门」的真实语义不是"无鉴权"，而是"所有人共享一个满额租户"** —— 这个语义在代码里成立，但它**没有任何地方这样写**。注释写的是「`REQUIRE_API_KEY=0` 显式关闭」，运维读起来就是"没有鉴权"，而实际得到的是"人人都是 default 租户"。这才是本项定为 P1 的真正理由：**不是默认值太弱，而是弱默认值的失败模式没有被说出来。**

## A 组（必做，零行为变更）

### A1 `default_key` 哨兵值：危险配置**响亮失败**，且不误伤合法用法

**问题：** `default_key` 是编译期常量，广泛出现在 SDK 默认值／脚本／文档里。若简单地把「配了 `default_key` 就拒绝启动」，会打断**所有**本机开发与本仓自身的自检（实测 60 次回归全部用它）。

**修法（把「危险」精确化，而不是「罕见」化）：** 判定为危险的**不是"用了 `default_key`"，而是"用了 `default_key` ＋ 把配额开满 ＋ 非 loopback 监听"**三者同时成立。

- 新增哨兵常量（如 `TENANT_SENTINEL_QUOTA = 10_000`），启动时自检：注册租户若 `api_key == DEFAULT_API_KEY` **且** `qps >= 哨兵` **且** 并发同量级 **且** 监听地址**非回环** ⇒ 打 **`warn!`**，并在日志里**逐条给出整改动作**（改 `API_KEY` env／收配额／改绑 `127.0.0.1`）。
- 为何不直接拒绝启动：非回环 ＋ 满配额 ＋ 默认 key 确实是真实事故组合，但**直接 panic 会让存量部署升级即挂**，违反本轮铁律。`warn!` 让"静默敞开"变成"日志里明写敞开"——这是**零行为变更**前提下能拿到的最大收益。
- 为何不加"必须改"的硬门：那属于**行为变更**，需要显式决策与迁移期（本轮不做，作为 OPT-R13 候选，需用户拍板）。

### A2 补上缺失的**语义文档**：`REQUIRE_API_KEY=0` 到底意味着什么

`docs/OPERATION.md`／`docs/USAGE.md` 现在只写「显式关闭鉴权门」。需**明确写出**：

- 门关时无头请求 → **自动获得 default 租户**（`qps/并发 = 10000/10000`）⇒ 等价于"全网共享一个满额身份"；
- 因此 `REQUIRE_API_KEY=0` **只能**用于**本机开发／隔离网络**；生产必须 `API_KEY=<强随机>` 并保持门开；
- 生产清单：监听回环或前置 mTLS／WAF；配额按租户下发；`X-API-Key` 出站前被摘除（`request_filter` 末尾 `remove_header("X-API-Key")`，已核实正确，**不要**改）。

**门禁：** 新增 `tools/check_auth_docs.py`，断言上述三个要点在 `OPERATION.md` ＋ `USAGE.md` 中英双语齐全，并断言**旧的不准确表述已消失**（反向断言）。这是本组唯一"防失实"的门，与 OPT-R10 的署名校验门同类。

### A3 常量单一真源

`DEFAULT_API_KEY` 现定义在 `gateway.rs`（数据面模块），却被 SDK／脚本／文档当公共约定引用。移到一个语义正确的位置（`tenant.rs` 或新 `auth` 模块），并全仓改为引用，杜绝"数据面模块持有鉴权公共常量"这一结构性错位。**纯搬迁，行为不变。**

## B 组（可延后，需用户决策）

- **B1 `API_KEY` env 覆盖**：让部署方**不必改代码**即可换掉弱默认值。这是解决根因的正路，但会**改变现有 `X-API-Key: default_key` 调用方的行为**（若部署方设了 `API_KEY`，旧客户端的 `default_key` 就 403 了）。⇒ 属行为变更，**需显式决策**，本轮只写进文档作为建议。
- **B2 常量时间比较**（`subtle`）：**明确不做**。已核实 `tenant.rs` 用 `DashMap::get` 哈希查找，攻击者须先猜中 SipHash 才有 key 比较，比裸 `String ==` 安全；`subtle` 会为一个**不存在的威胁模型**扩大供应链面。**不因"看起来该有"就加。**
- **B3 内建 Key 熵自检**：若未来支持 `API_KEY`，应校验其最小熵/长度（拒绝 `default_key` 这类字典值）。与 B1 同批。

---

## C 组（用户若选择"真收紧"时的迁移设计，本轮只出方案不实施）

若决定取消弱默认，正确顺序必须是：① 引入 `API_KEY` env（**先支持、再废弃**）；② 双 key 并存期（`default_key` 与新 key 同时有效，打 deprecation `warn!` 并计数）；③ 观测一个发布周期确认无旧客户端；④ 才移除 `default_key`。**任何一步跳过都会打断存量客户端。** 本轮不实施。

## 4. 验收标准

- `cargo fmt --check`、`clippy -D warnings`、`test --locked --workspace`、`bench --no-run` 四门绿（基线：252 passed / 7 ignored）。
- A1 哨兵自检：单测覆盖 8 种组合（默认/自定义 key × 满/低配额 × 回环/非回环），**断言"该响的响、不该响的不响"**（防"到处 warn"式的噪音门）。
- A2 文档门 `tools/check_auth_docs.py` 双向验证（删掉要点 ⇒ 判红）。
- 活流量回归：`REQUIRE_API_KEY=0` 下无头请求**仍 200**（证明零行为变更）；门开时无头仍 403、带 key 仍 200。
- 单测数变动后同步 `docs/QUALITY_BASELINE.md` 并让 `check_doc_consistency.py` 绿。

## 5. 明确不做

| 项 | 理由 |
| -- | ---- |
| 常量时间比较 | 威胁模型不存在（哈希查找已优于 `==`） |
| 直接拒绝 `default_key` 启动 | 行为变更，会让存量部署升级即挂 |
| 内置 `API_KEY` env | 行为变更（会 403 掉旧客户端的 `default_key`），需决策 |
| 弱化配额默认值 | 与"存量行为零变化"冲突 |

## 6. 附带项（P2，本轮只记录不修）：LinUCB 探索退化

OPT-R11 真实回归中实测：无约束 60 次请求 **60/60 命中同一节点**。经 pre-B1/B1 双二进制 A/B 证明**与 B1 无关**，根因已定位到算式：

```
compute_ucb_score = expected_reward + alpha*variance - 0.05*cost_weight
cost_weight_for_tier: datacenter 0.1 / residential 1.0 / mobile 3.0
```

在奖励信号尚未拉开差异时，三臂的 `expected_reward` 与 `variance` 相同 ⇒ **分数只由 tier 成本决定** ⇒ LinUCB 的"探索"退化为"选最便宜档"。奖励回写确实存在（`gateway.rs` 调 `arm.update(context, compute_reward(status, duration))`），但烟囱环境下三臂奖励几乎相同，压不过 0.045 的 tier 成本差。

**这是设计问题而非 bug**（成本优先本就是设计意图），但"探索项被成本项淹没"意味着**在成本同档的节点之间 bandit 不会分散**。修法需改探索项标度或给 `variance` 加下界，属**算法语义变更**，应单独立项并配 A/B 评估，不在本轮搭车。
