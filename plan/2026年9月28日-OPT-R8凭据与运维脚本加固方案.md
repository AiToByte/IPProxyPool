## 关键设计决策（先定口径，再动手）

### 决策 1：凭据不出 argv——为什么 `REDISCLI_AUTH` 是正解而非引号转义

**现状（实测清单）**：

| 位置 | 形态 | 泄漏面 |
|---|---|---|
| `docker-compose.yml:12` | `redis-server --requirepass ${REDIS_PASSWORD}` | `docker inspect` / 进程 argv |
| `docker-compose.yml:16` | `redis-cli -a ${REDIS_PASSWORD} ping`（healthcheck） | `docker inspect` 的 healthcheck 段 |
| `docker-compose.yml:111` | `REDIS_URL: redis://:${PASSWORD}@redis:6379/` | `docker inspect` 环境变量 |
| `ipp.ps1:78/102`、`backup.ps1:58` | `docker exec ... redis-cli -a "$env:REDIS_PASSWORD"` | 宿主 `Get-CimInstance Win32_Process`／`/proc/<pid>/cmdline` |
| `ipp.ps1:79`、`backup.ps1:68/74` | `curl --user "$u:$p"` / `clickhouse-client --password` | 同上 |

**为何引号转义不解决问题：** 即便把密码加引号，它仍在 argv 里，任何能读进程列表的人都能拿到。**必须让密码不出现在命令行本身。**

**修法：**

- **Redis CLI** → `REDISCLI_AUTH` 环境变量。Redis 官方为此专设的环境变量：设置后 `redis-cli` 自动用它认证，**命令行不含密码**。经 `docker exec -e REDISCLI_AUTH=...` 传入。
- **Redis 服务端** → `--requirepass` 仍在 argv（redis-server 无 env 替代）。**这是 redis-server 的限制**，无法用 env 规避。折中：改用**配置文件** `redis.conf`（`requirepass` 指令），密码只在文件里（文件权限 0600），不进 argv。compose 以 `command: ["redis-server", "/usr/local/etc/redis/redis.conf"]` 启动，配置文件由 `tools/gen_redis_conf.ps1` 或手工从 `.env` 生成并 gitignore。
- **ClickHouse client** → `clickhouse-client` 支持 `--password` 但**也支持配置文件** `~/.clickhouse-client/config.xml` 的 `<password>`，或 `CLICKHOUSE_PASSWORD` 环境变量（CH 24 client 支持）。经 `docker exec -e` 传入最简。
- **`curl --user`** → 改用 `--netrc-file` 或把凭据放进 `Authorization` 头（头也可能出现在 argv…）。最简：`curl -H "X-ClickHouse-User: ..." -H "X-ClickHouse-Key: ..."`，头值不出现在 argv。

**边界（诚实标注）：** 容器**环境变量**本身仍可被 `docker inspect` 读到（这是 Docker 的固有行为，无法在 compose 层消除）。本项消除的是**进程 argv** 这一最易泄漏面（同机任意用户可读 `/proc`/WMI），把暴露面从「同机任意用户」缩小到「有 Docker 权限者」。**真正的密钥管理需 Docker Secrets / K8s Secret，属更大改动，本轮不涉及。**

### 决策 2：`backup.ps1` 静默备份空卷——为何「校验」比「参数化」更重要

**现状（`backup.ps1:78/83`）：** 硬编码 `ipproxypool-gw-r1_clickhouse-data`。若用 `-p other` 或设 `COMPOSE_PROJECT_NAME`，`docker run -v` 会**自动创建一个空卷**（Docker 行为），tar 打包空目录，脚本照常打印 `"clickhouse freeze+volume done"` 与 `"ALL BACKUP DONE"`。

**双重修法（两者都要）：**

1. **参数化**：卷名从 compose 实际项目名推导（`docker compose config --format json` 或 `docker inspect` 当前容器拿真实挂载），而非硬编码。
2. **存在性与非空校验（更关键）：** 备份后**必须校验**产出的 tar 非空、且含预期条目数；任一不满足即抛错退出。这样即便未来又有新的路径错误，也不会再「静默备份空卷却报成功」。

**校验口径：** `tar -tvf` 列条目数 > 阈值（CH 库至少应有 `store/` 与 `metadata/` 目录；Grafana 至少应有 `grafana.db`）。任一缺失 → 报错退出非零。

### 决策 3：看护探针去 mock 化——为何「端口归属 + 进程签名」双判据

**现状（`ipp_watchdog.ps1:68-83`）：** `Test-GatewayIdentity` 要求响应体含 `mock-`，否则返回 `404-foreign`；主循环遇到非 200 且非自身进程即累计 strike，满 3 次重拉。

**缺陷：** `docs/OPERATION.md:42-43` 的真 Key 灰度流程第 2 步要求「把 `mock-x` 换成真实 `ip:port`」，换完后响应体永远不含 `mock-` ⇒ `Test-GatewayIdentity` 恒返 `404-foreign` ⇒ **每 3 轮（约 90s）重拉一次进程，无限循环**。

**修法（两级，缺一不可）：**

1. **端口归属判据（主）**：检查监听 `127.0.0.1:8916` 的进程是否为本仓启动的 `pingora-proxy-gateway`（比对可执行文件路径 / CommandLine 含本仓 target 路径）。这与响应内容**无关**，是客观事实。
2. **进程签名（辅）**：`mock-` 前缀仅作为**日志指纹**记录，不再作为存活判据；对真供应商部署自动关闭该判据（检测到响应体非 mock 时**只记日志不判失败**）。

**为何不能只留端口归属：** 若别人占用了 8916 端口，端口归属会误判为「我方进程存活」。故两条都留——端口归属判「是不是我」，HTTP 探活判「还能不能服务」。

### 决策 4：`ipp_free_test.ps1` 空响应判 CLEAN——为何默认必须是「未知」

**现状（`:50-58`）：** `$verdict` 初始值 `"CLEAN"`；`-match` 对 `$null` 返回 `$false`，于是**网关请求失败（502/503/超时）时判定停留在 `CLEAN`**。一个「证明免费出口干净」的脚本把完全失败的请求判为干净通过——**失败方向与安全方向相反**。

**修法：** 三态判定 `CLEAN` / `SUSPECT` / `TRANSPARENT`，**外加 `UNKNOWN`**；任何无法取到响应体的情况一律 `UNKNOWN` 且**退出码非零**（默认失败）。安全相关的判定必须「默认不通过」。

### 决策 5：`restore.ps1` 真恢复——为何仍保留 dry-run 为默认

有备份无恢复＝灾备能力是纸面的。但**真恢复是高危操作**（会覆盖/替换现网数据）。故：实现 `-Execute` 路径，但**默认 dry-run 只打印计划**；`-Execute` 需显式传参且执行前强制二次确认（`Read-Host` 校验输入 `RESTORE`），并在执行后**自动跑一次行数对账**。

## 执行后的增补说明（诚实记录）

1. **A1 的原方案（Redis 配置文件）被降级**（设计变更，如实说明）：原计划写「新增 `deploy/redis/redis.conf` ＋ `tools/gen_redis_conf.ps1`」。执行时确认 **`redis-server --requirepass` 无环境变量替代**（Redis 自身限制），要真正规避 argv 需配置文件＋挂载＋生成器，属更大改动（引入新文件＋新生成流程＋首次部署文档更新），超出本轮「不新增流程」的克制边界。故 A1 **只做 healthcheck 侧**（可干净落地），`redis-server` 的 argv 泄漏**保留**并在 compose 注释中标注。这与原计划有出入，如实登记。
2. **A5 断言自身经历 3 轮修正**（值得记录，因为它就是 CI 门禁的典型迭代）：
   - 第 1 轮：误报自己（脚本文档字符串里含违规样例字面量）→ 加「排除自身」；
   - 第 2 轮：`live.yml` 的 `$$CLICKHOUSE_PASSWORD`（容器 env 引用，**正确形态**）被误判 → 放宽为「变量引用即放行」；
   - 第 3 轮：反向验证时发现**真实漏检**——`docker exec ... redis-cli -a "$env:PASSWORD"` 被第 2 轮的 `$env:` 规则误放行。补「`$env:` 必须与 `docker exec -e VAR=` 同行才算安全注入」。
   ⇒ **断言的价值不在于一次写对，而在于用「正向 0 误报 + 反向必抓」双向实测校准**。只跑正向会写出自欺欺人的门禁。
3. **B1 第一道闸最初是失效的**（实测打脸）：原写 `if (-not (docker volume inspect $v 2>$null))`。本机实测 **`docker volume inspect` 对存在的卷也返回 exit=1 并向 stderr 写告警**，导致输出非空、`-not` 恒 false、闸门形同虚设，空卷照旧被创建。改用 `docker volume ls` 列取比对（无歧义）后生效。**这正是「两道闸」设计的价值**——第一道失效时第二道仍抓住了空卷。
4. **项目名解析连续踩了两个坑**（`backup.ps1` 与 `restore.ps1` 同源，已同步修正并留注记）：
   - `docker inspect -f "{{ index .Config.Labels \"com.docker.compose.project\" }}"` 在本机返回 **0 行**（PowerShell 双引号串里 `\"` 不构成对 docker 的转义）；
   - 改简化模板 `{{.Config.Labels.com.docker.compose.project}}` 返回字面 **`<no value>`**（键名含点被当嵌套路径）。
   ⇒ 最终用 `docker inspect` 全量 JSON ＋ `ConvertFrom-Json` 直读标签（本机实测正确）。
5. **一处 PowerShell 续行符陷阱**（输出里出现孤立 `+` 行）：`Write-Output "text " + $var` 的行尾 `+` 被 PowerShell 当作**续行符**。改用 `"text $($var)"` 子表达式。全仓 `tools/*.ps1` 已扫，无其他同类。
6. **一次虚惊如实记录**：验证 restore 时报「backup incomplete（tar MISSING）」，排查后确认是**我并发调用了两次 backup**、后一次尚未写完 tar 即被读取——**非脚本缺陷**。但它恰好证明「产物完整性校验」这道闸有效：真的缺产物时它会拒绝恢复，而不是拿半成品继续。
