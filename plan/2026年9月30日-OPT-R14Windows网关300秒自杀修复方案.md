# OPT-R14 方案：Windows 下网关 300 秒自杀（P0，可用性）

> **来源:** OPT-R14 前置勘察（用户指定"先修 P0"）。
> **性质:** 这是**框架限制**，不是本仓逻辑缺陷；但**由本仓承担后果**（所有 >300s 的验证、压测、长跑都做不了，且现象像随机崩溃，极难定位）。

---

## 0. 根因（已定位到依赖源码行，非推断）

`pingora-core 0.6.0` `src/server/mod.rs` 的 `Server::run()`：

```rust
let shutdown_type = server_runtime
    .get_handle()
    .block_on(self.main_loop(run_args));
#[cfg(windows)]
let shutdown_type = ShutdownType::Graceful;      // ← Windows：无条件

if matches!(shutdown_type, ShutdownType::Graceful) {
    info!("Graceful shutdown: grace period {}s starts", exit_timeout);
    thread::sleep(Duration::from_secs(exit_timeout));   // ← 默认 300s
    info!("Graceful shutdown: grace period ends");
}
```

`run()` 结尾 `info!("All runtimes exited, exiting now")`，`run_forever()` 随即
`std::process::exit(0)`。

**即：Windows 上 `main_loop` 从不被 await（那段是 `#[cfg(unix)]`），因此没有信号等待、
`shutdown_type` 被硬编码为 Graceful，网关必然先 `sleep(GATEWAY_GRACE_SECS)` 再退出。**
本仓把 `GATEWAY_GRACE_SECS` 默认设为 300（优雅停机的合理值），于是**在 Windows 上
网关的寿命上限就是 300 秒**。

### 实测证据（本机，跨 FreePool 开关均复现）

| 日志 | 寿命(s) | 退出 | FreePool |
| ---- | ------- | ---- | -------- |
| `vfree.out` | 308 | EXIT | 开 |
| `vfree2.out` | 308 | EXIT | 开 |
| `r13gw.out` | 307 | EXIT | **关** |
| `gw-r11.out` | 305 | EXIT | **关** |
| `r13gw3` / `gw-r11b` | 245~270 | — | 关（我手动 kill，未到 300s） |

**四例退出寿命 305~308s ＝ 300s sleep ＋ 数秒启动**，与 FreePool **无关**。

> **顺带纠正一个我自己先前的误判：** 我一度认为退出与 FreePool 相关（只有开了
> FreePool 的 `vfree*` 出现退出）。那是**伪相关**——只是那几次跑得够久。跨
> FreePool 开关的四例都退出后，相关性被证伪。此处留档以免下一个人重犯。

### 顺带排除的一个怀疑（避免下一个人重查）

2026-09-23 的旧日志 `log/gw-demo-end.err` 末尾有
`Cannot drop a runtime in a context where blocking is not allowed`。
**当前代码不会触发它**：`main()` 是 `let server = runtime.block_on(setup_gateway());
let _keep_alive = runtime; server.run_forever();` —— `run_forever()` 跑在**同步**
`main` 上下文，`server_runtime` 的 drop 不在 async 上下文内。那句 panic 属**旧代码
状态**的产物（推测当时是 `block_on(async { run_forever().await })`）。
**本轮不据此改代码**，仅记录。

## 1. 修法：平台感知的默认 grace period ＋ 响亮告警

**不做的事（先说清，避免误选）：**

- ❌ **把默认改成 0**：Windows 上会**立刻退出**，比现状更糟。
- ❌ **升级 Pingora**：需联网解析新版本并重新验证整条数据面（成本高、风险大），
  本轮不做；**登记为后续候选**。
- ❌ **自己重写 server 驱动**：等于 fork 框架，代价与风险都不成比例。

**选定修法：** 保持 `GATEWAY_GRACE_SECS` 可覆盖，但让**默认值按平台区分**，并在启动时
**明确告警**该限制。

| 平台 | 默认 `GATEWAY_GRACE_SECS` | 语义 |
| ---- | -------------------------- | ---- |
| Unix | **300**（不变） | 真正的优雅停机等待窗口 |
| Windows | **86400**（1 天） | **仅为绕过框架的自杀行为**；Unix 上同样的值无意义 |

- 选 86400 的理由：本机用途是开发/验证，"最多活一天"实际等价于"不会自己死"；
  同时它是**显式可覆盖**的（`GATEWAY_GRACE_SECS=0` 仍可让 Windows 上立即退出，
  便于测试）。
- 启动时打 `WARN`，写明：这是 Pingora 0.6 在 Windows 上不等待信号、必然
  `sleep(grace)` 后退出的限制，以及"这不是你的配置错了"。
  **不响亮 = 运维会以为是随机崩溃**，这正是本项此前难定位的原因。

**行为影响声明：** Windows 上网关寿命由"≤300s"变为"≤86400s"。这是**有意的行为变更**，
用"可用"换"5 分钟自杀"。Unix 行为**零变化**。

## 2. 实施要点

- **B1**：抽纯函数 `default_grace_secs(is_windows: bool) -> u64`（便于单测穷举两平台），
  `main.rs` 改为 `env_secs("GATEWAY_GRACE_SECS", default_grace_secs(cfg!(windows)))`。
  ⚠️ 用 `env_secs`（非法值回落默认）而非手写 parse，保持与既有风格一致。
- **B2**：启动 `WARN`（Windows 分支）说明框架限制 ＋ 覆盖方法。
- **B3**：单测——两平台默认值；显式 env 覆盖优先于平台默认；
  `default_grace_secs` 不返回 0（否则 Windows 立即自杀）。
- **B4**：契约门 `tools/check_windows_lifetime.py` 断言
  ①平台感知默认值仍在（防止被"简化"回 300 导致 Windows 静默自杀）；
  ②`docs/OPERATION.md` 写明该限制与覆盖方式。
- **B5**：**活流量验证（本项唯一决定性证据）**：改完后让网关跑 **> 330 秒**
  （原必死的区间）并确认仍在服务 + metrics 可读。

## 3. 验收标准

- 四门绿（基线 262 passed / 7 ignored）；10 个分配/契约门全绿。
- `default_grace_secs` 三类单测全绿。
- **活流量：t=340s 时网关仍响应 200 且 `/metrics` 可读**（这是本项的核心验收，
  失败即等于没修）。
- `check_windows_lifetime.py` 双向验证（改回 300 / 删文档限制 ⇒ 判红）。
- 文档：OPERATION 写明 Windows 限制、`GATEWAY_GRACE_SECS` 覆盖方式、
  以及"升级 Pingora"是长期修法。
