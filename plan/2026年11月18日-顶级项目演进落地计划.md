# IPProxyPool 顶级项目演进落地计划

**建立日期：2026-11-18**  
**依据：** `docs/WORLD-CLASS-ASSESSMENT.md`、`docs/CAPABILITY-AUDIT.md`、`docs/ROADMAP-FOUR-TRACKS.md`、`plan/2026年11月13日-世界级生产可信化与渐进式演进方案.md`，以及 2026-11-15 Linux 验证计划和其后续执行记录  
**状态：** E0 已完成；E1 admission gate、有界 shutdown flush、required Redis fail-fast 与 CONNECT 关停边界拆分已实现并通过本地 Windows 行为/启动测试；Linux/live drain 验证、shutdown/启动 race 关闭、严格 admission 线性化和 bounded in-flight drain 仍待完成  
**复杂度：** Large / 多阶段产品与可靠性演进  
**执行规则：** 本计划是路线与阶段门，不授权一次性实现所有阶段。每个实现切片需先校验工作树、明确范围、记录 RED、通过 GREEN、独立 review，并经适用的真实依赖/平台门验证。

## 1. 目标与非目标

将 IPProxyPool 从“功能较丰富、以单实例为主的智能代理网关候选实现”推进到可被团队部署、运维、升级、对账和回滚的生产平台。评价目标是**可证明的安全性、可靠性和可运维性**，不以新增协议、代码量、测试数量或单机峰值 QPS 代替生产成熟度。

本计划优先补齐：

1. 当前能力和文档的证据一致性；
2. 安全默认、目标/出站策略和密钥运维；
3. readiness、admission、drain、恢复和数据对账；
4. 版本化控制面、身份/审计和跨实例边界；
5. 可重放、可对账的遥测与 usage ledger；
6. 有统计纪律的路由策略灰度；
7. 独占 Linux 环境上的容量、长稳和发布回滚证据。

明确不做：

- 不为了“世界级”重写 Pingora、Redis 或 ClickHouse；
- 不在缺真实需求和 T1 前置门未关闭时实现 H2/H3、QUIC、CONNECT-UDP/IP、MASQUE 或 MITM；
- 不把公开免费代理源当作稳定、授权或有 SLA 的供给；
- 不把静态 API Key + Redis balance 描述为企业 IAM 或金融账本；
- 不在现有繁忙物理服务器上做容量压测；
- 不覆盖当前未提交工作树中的文件或历史记录。

## 2. 项目基线与证据纪律

### 2.1 当前有据可依的能力

- `gateway/src/gateway/`：Pingora HTTP 代理数据面、鉴权、选路、上游、计量；
- `gateway/src/router/`、`gateway/src/bandit.rs`：加权、粘滞、约束、隔离和 LinUCB；
- `gateway/src/health.rs`、`gateway/src/admin/`：`/livez`、`/readyz`、旧 health 兼容、共享 readiness 决策；
- `gateway/src/telemetry.rs`、`gateway/src/ch_sink.rs`、`gateway/src/analytics.rs`：MPSC/Redis Stream/ClickHouse 遥测和 sink；
- `gateway/src/tenant.rs`、`gateway/src/node_registry.rs`：租户运行态和节点文件持久化；
- `docs/QUALITY_BASELINE.md`：当前权威测试数字为 `445 passed / 0 failed / 10 ignored`；该数字不是覆盖率或 SLA；
- 2026-11-16 的 Linux 隔离 builder 验证：fmt、Clippy、workspace tests、release build 通过；Linux workspace tests 为 `438 passed / 0 failed / 10 ignored`；该数字是当时历史证据，当前增量 E1 测试基线见 `QUALITY_BASELINE.md`。
- 同期隔离环境完成 Redis/ClickHouse readiness 和故障恢复、Gateway 探针、loopback 数据面及 graceful SIGTERM/精确强杀证据；容量测试因环境资源硬门未执行，测试环境已清理。

以上只表示已记录的特定版本/拓扑证据，不推导 HA、多实例账务、生产容量或商业 SLA。

### 2.2 规划和执行规则

- `docs/QUALITY_BASELINE.md` 是当前测试数字唯一真源；`COVERAGE_BASELINE.md`、`PERF_BASELINE.md`、`ROUTING_BASELINE.md` 分别限定覆盖率、性能和路由回放结论。
- 活能力状态使用 `DRAFT → FACT-CHECKED → APPROVED → RED-RECORDED → IMPLEMENTING → GREEN → REVIEWED → VERIFIED → CLOSED`。
- mock/stub、单测、Windows、Linux 构建、Linux live 依赖、生产流量是不同证据层，逐项标注，不互相替代。
- 故障注入、强杀、外部流量、容量测试、Docker 持久对象变更分别通过独立阶段门；不得从前一项批准推导后一项批准。
- 每次远端动作先核对 SSH key、主机身份、project/container ID、labels、端口和资源；不改 daemon 代理/网络，不碰 `/opt/service` 既有业务，不做全局 prune。
- 计划每个切片明确：影响文件、RED/GREEN、live 需要、回滚、文档和证据责任人/状态。

## 3. 当前项目模式：命名、错误、日志、数据与测试

| 类别 | 仓内模式 | 规划要求 |
|---|---|---|
| Naming | Rust 文件/模块按领域分解，如 `gateway/src/health.rs`、`startup_config.rs`、`node_registry.rs`；环境变量为大写下划线 | 继续沿用现有领域模块与既有 env 命名，不新增第二套配置抽象 |
| Errors | startup preflight 对非法配置给固定字段诊断；Admin handler 返回稳定状态码/body；异步后台由 supervisor 管理 | 新错误保持 fail-closed/明确 degradation；不回显凭据、含 secret URL 或任意输入 |
| Logging | 以 `log`/`env_logger` 输出；Admin audit 记录固定 path/status，不记录 Key | 结构化字段保持低基数；新增日志需可关联 request/event，但不含 secret、完整 URL/query、原始代理凭据 |
| Data access | Redis Streams consumer group、PEL/ack；ClickHouse sink；节点文件通过 `NodeRegistry` 原子持久化 | 明确事实来源、幂等键、版本和恢复语义；账务事实不得只依赖异步缓存 |
| Tests | Rust `#[cfg(test)]` 单测/子进程；live 依赖测试标记 ignored；Python gate 位于 `tools/` | 新行为优先表驱动/状态矩阵；外部行为必须用黑盒测试；live 与 mock 明确分栏；同步 `QUALITY_BASELINE.md` |

### E1：T1 运行状态、admission、drain 与生命周期完整收口（最高优先级）

**当前实现进度**：HTTP 与 CONNECT admission gate、有界 tenant flush helper、required Redis fail-fast 与 CONNECT 生命周期阶段拆分已落地并通过本地 Windows 行为/启动测试；握手前由 `ShutdownWatch` 取消，`200` 已刷出后由 `EstablishedTunnel` 持有 relay 与结算守卫。该进度不是完整 E1 closeout。

**目标**：readiness 不只反映探针返回，而真实控制新请求接受/停止；优雅关停和强制退出语义有界、可测。

**动作**：
1. 盘点 `gateway/src/health.rs`、`gateway/src/main.rs`、`gateway/src/admin/handlers_ops.rs`、`gateway/src/connect.rs`、`gateway/src/gateway/` 的当前状态更新点。
2. 建立显式 lifecycle state，统一 `Starting / Ready / Degraded / Draining / Stopping / Stopped` 的所有权和转换；消除未使用 setter/实际 listener readiness 断裂。
3. 把 readiness withdrawal 与 admission gate 绑定：进入 draining 后拒绝新代理请求/隧道；已有请求只在预算内完成；CONNECT（若在本轮构建中启用）单独验证 tunnel 行为。
4. 对 SIGTERM/Ctrl-C 统一顺序：unready → close admission → stop timers/supervised workers → bounded flush → close listeners → exit；所有 wrapper/init 进程必须正确 signal-forward。
5. 为 Redis required/optional、ClickHouse optional、listener probe 失效与恢复增加明确 decision table，特别验证 `TENANT_STORE=redis` 缺 Redis 时实际 readiness/admission 行为，不把 503 等同 admission 已关闭。
6. 对 graceful 与强杀路径分离验收；强杀只作用于已核验测试容器/PID，并独立批准。

**候选文件**：`gateway/src/health.rs`、`main.rs`、`admin/handlers_ops.rs`、`admin/mw.rs`、`connect.rs`、Gateway admission hooks/tests、`docs/ADMIN_API.md`、`docs/OPERATION.md`。

**RED/GREEN**：先增加状态矩阵和黑盒进程测试；必须观察到 draining 时 `/readyz=503`、live 在 event loop 存活期仍 200、新 admission 被拒绝、已有请求有界结束；Redis required down 返回 503 且不继续接受受保护流量；SIGTERM 后无 worker respawn/进程泄漏。

**退出门**：Windows + Linux 分别验证；Linux 使用隔离真实 Redis/ClickHouse；任何未执行的 kill -9 / Ctrl-C 场景标 `NOT RUN`，不声称 complete drain。

**回滚**：保留旧 probe 路由兼容；回滚 admission/lifecycle 切片需同时回滚对应 readiness 声明，禁止仅回滚实现造成 readiness 假绿。

### E2：安全默认、secret lifecycle 与出站策略

**目标**：开发便利与生产 fail-closed 分离，避免默认 Key、开放绑定或代理目标变成生产安全隐患。

**动作**：
1. 明确开发/生产配置 profile；生产启动拒绝 `default_key`、`123456`、`change-me-*` 等 placeholder。
2. 明确 Redis/ClickHouse URL 凭据、Admin Key、API Key 的来源/轮换/撤销/审计；日志、错误、诊断、metrics 全面脱敏。
3. Admin 只允许 loopback 或受 TLS 保护的可信入口；文档不把明文非回环 HTTP 描述成安全配置。
4. 设计统一 `EgressPolicy`：DNS resolve、IPv4/IPv6 规范化、private/link-local/loopback/metadata 拒绝、DNS rebinding 复核、端口 allow/deny、redirect 重新校验、tenant/provider policy。
5. 给所有免费池抓取、出口探测、代理上游和 redirect 统一网络边界；synthetic mock 默认不得出容器隔离网络。
6. 添加配置级审计和 secret scanner 用例，确保仓库无真实节点、代理凭据、部署 `.env` 或认证材料。

**候选文件**：`startup_config.rs`、`gateway/upstream.rs`、`free_pool/` source/verify、`prober.rs`、Compose profile/docs、`tools/check_no_plaintext_creds.py` 及测试。

**退出门**：负向 SSRF/DNS/private IPv6/metadata 测试通过；无 secret 回显；生产配置弱凭据 fail-fast；Admin 传输边界经 security review。

**回滚**：新策略先 observe-only/deny-by-default 分批启用；只回滚策略版本，不回退证书验证或脱敏保护。

### E3：遥测语义、数据对账、告警接收和 Runbook

**目标**：让请求、遥测、Redis pending、ClickHouse row、告警形成可重放和可对账的运维证据链。

**动作**：
1. 为请求、attempt、telemetry event 定义稳定 `event_id`/correlation ID 和 schema version；现有 `X-Trace-Id` 不直接宣称 W3C trace。
2. 建立 event manifest 或可复核身份，记录 stream ID、sink batch ID、insert result、ack result、replay/duplicate；明确 at-least-once，除非幂等性有行为证明，不声称 exactly-once。
3. 为 Redis trim/deleted PEL、pending age、consumer restart、sink retry、ClickHouse response-loss 增加计数/日志/恢复时间。
4. 指标仅使用低基数固定 label；禁止 tenant ID、URL、目标域、Key、出口 IP 等无界标签。
5. 为 request success、429、upstream 502/504、ready ratio、telemetry drops/lag、sink last-success 建 SLI/SLO 候选，并明确错误预算与 owner。
6. 验证 Prometheus → Alertmanager → 实际 receiver 的投递；没有 receiver 时标记“无 paging”。
7. 写并演练 runbook：启动失败、Redis/ClickHouse degraded、积压、数据对账、凭据轮换、配置回滚、证据保存。

**候选文件**：`telemetry.rs`、`ch_sink.rs`、`analytics.rs`、metrics、Prometheus rules、Alertmanager config、`docs/OPERATION.md`、`QUALITY_BASELINE.md`。

**退出门**：一次可控 synthetic batch 从请求到 Redis 到 ClickHouse 对账；故障期间 ACK/PEL 语义和丢失/重复可解释；真实告警 receiver 成功，或显式记录 NOT CONFIGURED。

**回滚**：指标/schema 采用 additive migration；保留旧字段读取兼容；禁止清空 PEL/生产表进行回滚。

### E4：版本化控制面、RBAC 与配置发布

**目标**：将目前单实例节点热更新拓展为可审计、可回滚的配置发布基础，不直接克隆 Envoy xDS。

**动作**：
1. 分离配置意图、运行健康、自动路由决策、账务状态四类数据所有权。
2. 设计 `ConfigSnapshot`：version、schema_version、parent_version、content_hash、created_by、审批状态、发布时间、回滚目标；不包含 secret 明文，只存 secret reference。
3. Admin API 支持 draft/validate/publish/rollback，校验失败返回 NACK 和固定错误字段。
4. 多实例 ACK/NACK、instance version、过期/失联实例、漂移检测和发布超时。
5. 加 OIDC/SSO 或企业 IdP 接入边界、RBAC（viewer/operator/billing/admin）、service account、key rotation/revocation、审计主体。
6. 前端只展示服务端权限结果；所有 mutation 路由在后端校验角色与资源 scope。
7. 单实例先落地 schema/version/rollback；多实例发布留到真实多节点环境，禁止用单机多容器冒充 HA 证明。

**候选文件**：`gateway/src/admin/`、`node_registry.rs`、新 `config_snapshot` 域模块、Admin DTO/OpenAPI、`web/admin/`、migration/docs。

**退出门**：RBAC 正/负集成测试；配置校验、发布、ACK/NACK、rollback 行为测试；secret 不进入导出；两个真实实例同步与漂移演练通过后，才宣称多实例配置能力。

**回滚**：Snapshot 保留上一个可用版本；发布可原子回退；schema 只做前向兼容 migration。

### E5：运行时配额与账务事实分离

**目标**：避免把 Redis 异步 balance 当作结算账本，明确多实例并发和事件幂等语义。

**动作**：
1. 保留 Redis 作为低延迟运行态 quota/cache；定义 append-only usage ledger 作为账务事实候选。
2. 每个 usage settlement 有稳定 ID、tenant scope、policy/price version、请求/attempt 关联、字节数、金额、状态、重试次数。
3. 设计 reservation → commit/settle → compensation；取消、重试、上游失败不得双扣/漏扣。
4. 多实例并发用数据库事务/幂等写入证明一致性；Redis 与账本定期对账并能修正。
5. 区分代理成功、HTTP status、上游已发送字节、用户已计费字节；重试不可重复计费。
6. 在一致性、恢复、审计未过前，产品声明继续限定为“单实例 quota/metering”，不称 financial ledger。

**候选文件**：`tenant.rs`、`gateway/hooks.rs`、Admin balance API、ledger schema/repository、settlement tests、运维对账文档。

**退出门**：并发请求、进程中断、Redis 重启、重复 event 重投和补偿场景全通过；金额/字节与独立账本 SQL 对账精确。

**回滚**：新账本先 shadow-write；确认对账后再作为 source of truth；保留旧 Redis key 做回退窗口，不允许双系统同时各自扣款。

### E6：LinUCB/策略因果评估与灰度

**目标**：把算法微基准和合成 replay 与线上收益证明分开，建立可审计、可回退的路由策略验证方法。

**动作**：
1. 每次 decision 记录 policy_version、候选摘要、chosen node、score/reason、propensity、attempt、outcome/error、成本和延迟；禁止无界标签。
2. 用真实可授权流量建立脱敏 trace dataset；记录过滤偏差、缺失样本、时间窗和 provider 变化。
3. 对 round-robin/weighted/LinUCB 建固定 seed replay、holdout 和置信区间；补 propensity/反事实偏差评估。
4. shadow decision 不改变流量；对照当前策略结果，不把 synthetic replay 作为业务因果结论。
5. 独占 staging 先 1% canary，定义成功率、p99、403/429、成本、供应商故障停止阈值和自动 rollback。
6. 探索/利用策略及自动权重作为独立 policy version 管理；不得因人工调权与 SLA 自动动作混淆。

**候选文件**：`bandit.rs`、router、telemetry schema、`tools/routing_replay.py`、`tools/replay/` fixture、路由基线和 canary runbook。

**退出门**：策略结果可重放、版本可关联、holdout 统计方法 review 通过；生产效果须有 canary/rollback 证据。

**回滚**：每个租户/provider 有固定策略 fallback；异常时即时回到 weighted/sticky 基线，不清除学习数据。

### E7：独占 Linux 容量、长稳与发布准入

**目标**：从“能在 Linux 构建/故障恢复”推进到“该版本在声明拓扑和负载下有可重复运行证据”。

**动作**：
1. 使用独占或隔离 Linux 主机；当前共享业务机可作功能验证，不做容量压测。
2. 比较无 Gateway ground truth 与 Gateway：telemetry off、Redis telemetry on、Redis+ClickHouse sink on；真实上游仅用明确授权 fixture。
3. 并发 1/4/16/32/64，先 10 秒 smoke 再按批准 60 秒；单独报告限流 429 和路径饱和。
4. 增加至少 24 小时低负载 soak，监测 RSS/FD/task/connection/queue/PEL/lag/drop/restart。
5. 建立版本 pin、SBOM、镜像 digest、构建 provenance、advisory/license gate、签名和回滚 binary/config。
6. Canary 先小比例，定义停止阈值、旧版本回滚和数据兼容；执行一次演练。

**退出门**：硬件、kernel、commit、配置、上游拓扑、流量和测量脚本全记录；SLO/容量声明可复现；异常阈值和回滚实际通过。当前物理机可用内存曾低于 6 GiB 硬停止阈值，不得在其上启动容量负载。

**回滚**：binary/config/DB schema 分别回滚；必要时只停止测试客户端和测试 Gateway；不触碰现有生产服务。

### E8：协议扩展（需求触发后独立立项）

先 TLS 入站与 HTTP/1.1 CONNECT 标准客户端验收，再按客户/互通需求评估 H2 CONNECT、H3、PAC、CONNECT-UDP/IP。每个协议单独 threat model、互通矩阵、状态码/隧道/计量/关闭语义和 rollback。默认不做 MITM；不得把“有 CONNECT listener”宣传成完整浏览器代理支持。

## 8. 模式对照与测试要求

- **命名**：沿用 `snake_case` Rust 域模块、`StartupConfig`/`RuntimeFacts` 类型、env 大写下划线；状态采用 enum，不用多组松散 bool 表达互斥阶段。
- **错误处理**：延续 `startup_config.rs` 的纯解析/fixed-field error、`health.rs` 纯 readiness evaluator；handler 返回稳定状态/body，内部错误仅写脱敏日志。
- **日志**：沿用 `log`/`env_logger` 和 Admin audit 固定 path/status；禁止 secrets、凭据 URL、原始 Key、任意 domain/IP 放高基数 labels。
- **数据访问**：沿用 trait/manager 注入、Redis/ClickHouse 独立客户端、atomic file registry；新 ledger 不应通过直接散落 SQL/Redis key 绕过 repository/service 边界。
- **测试**：Rust 单测放领域模块 `#[cfg(test)]`；集成/启动顺序用子进程或 HTTP 黑盒测试；外部依赖 live 标记与 mock 分开；关键状态必须有 RED/GREEN 命令和实际退出码。

## 9. 风险、门槛和停止条件

| 风险 | 缓解/门 |
|---|---|
| 当前工作树存在未提交文件且 `EXEC_LOG.md` 有历史 | E0 前后记录 status；仅增量改动批准文件；历史留存，不做全文件重排 |
| 共享物理服务器上运行依赖影响其他 workload | 只用唯一 project/网络/卷、loopback 端口、资源限制；每次操作前核对 labels/IDs；容量工作转独占机器 |
| Docker/测试工具访问外网代理、基础镜像或 free proxy source | 默认关闭 free pool/外部探测；构建使用固定镜像 digest/批准路径；不改 daemon proxy |
| 测试凭据写入日志/仓库 | 仅临时 secret file/secret injection，0600；命令输出不渲染 secrets；结束后核对删除 |
| fault injection 目标识别错误 | 同时核 container ID、project label、service、image digest、volume/network；不确定则停止 |

### 11.2 E1 admission/drain 收尾（进行中）

**Redis 启动切片**：显式 `TENANT_STORE=redis` 必须连接 Redis 并在限定时间内完成租户状态加载，否则退出 `1`，不启动数据面或租户写回。`memory` 模式继续允许 Redis 缺失。先用实际可执行文件和回环替身跑 RED，再修改 `gateway/src/main.rs`；同步运维契约，不变更运行期探针策略或关停逻辑。回滚须恢复先前版本；不能用切换到 `memory` 假装保留持久化。

- 先修补 setup/shutdown 顺序：当前 signal watcher 与 Pingora 有独立信号监听，需检查 race，确保 draining 标记先于 listener/framework shutdown 广播生效；加入确定性同步测试。
- 明确 `TENANT_STORE=redis` 的准入和恢复契约：启动时若回退到内存，后续 Redis `PING` 成功不会重建 Redis 租户存储，不应单凭探针恢复就绪。先用本地测试验证这一差异；在确保持久化后端实际启用前，保持未就绪或拒绝启动。不要把所有 `/readyz=503` 状态同等处理。
- 若要把可选 CONNECT 纳入编排流量，需要独立确认其 listener 可用性；当前 `/readyz` 只探测主 HTTP listener。
- 为 CONNECT 加入“已有 tunnel 有流量时，第二个新 CONNECT 返回 503 且不拨上游”的同一 app 测试，并验证既有 tunnel 继续双向传输。
- 对 HTTP 使用 request_filter 同层测试和/或实际 Pingora local listener 测试；分别证明 drain 前已接纳的请求完成、drain 后的新请求被拒绝；不得在没有 Pingora lifecycle 行为证据时承诺 bounded completion。
- 对 5 秒 flush helper 做 success/error/timeout 三分支测试；确认 timeout 后取消语义、日志和 flush_dirty 的代价；实际子进程信号路径只在明确授权的本地隔离进程运行，不触碰远端容器/生产服务。
