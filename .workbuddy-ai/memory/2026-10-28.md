### 核心设计决策（不可轻易改动）
1. **只卡回退、不卡达标**：向上无门槛（绝对门槛会逼出无鉴别力的凑数测试），
   向下门槛 = 低于基线 1.0pp 判红。容差 1pp 而非 0（编译器/单态化噪声会周期性
   假红，假红门禁会被学会忽略）或 5（5pp 放过「新增 800 行 0 测试」）。
2. **总体覆盖率必须按行数加权重算**（`Σcovered/Σcount`），**不是**逐文件百分比
   的算术平均——`main.rs` 1737 行 vs `fingerprint.rs` 73 行，算术平均直接算错。
   基线里存 `_totals.lines` 真值，不现算。
3. **平台/工具链感知**：覆盖率数字跨工具链、跨平台**不可比**（单态化、内联决策、
   `cfg` 分支展开都会变）。按 rustc 版本 + 目标三元组判定：可比才做 [B] 数值判定；
   不可比时**只**做 [A] 文件集 + [C] 文档一致，并**显式打印**跳过原因，
   **绝不静默放行**。基线在 Windows/MSVC，CI 在 Ubuntu ⇒ CI 走「不可比」分支。
4. **自测 4 处注入**全部判红：覆盖率回退 / 基线文件缺失 / markdown-JSON 不一致 /
   「不可比模式只跳过数值判定」（锁住「跳过」只能跳过 [B]，若连 [A] 也跳过，
   「工具链不同」就成了绕过整道门的万能钥匙）。

## 2026-11-01 步骤 65：供应链——zstd 4 条公告的可达性论证与显式豁免 ✅

### 背景（一条重要教训）
`check_supply_chain.py` 此前**每轮都因离线拉不到 RustSec DB 而跳过**。
⇒ 门禁"绿"是**因为没跑**，不是因为没问题。本轮 cargo deny 用缓存库跑通才暴露 4 条。

### 4 条公告全部来自 zstd 生态（不是 pingora 本身）
| ID | 受影响符号 | 补丁 |
|---|---|---|
| 2026-0391 | `zstd::stream::raw::{Encoder,Decoder}::with_context` | zstd ≥0.14.3 |
| 2026-0398 | `zstd_safe::Seekable::decompress` | zstd-safe ≥8.2.0 |
| 2026-0403 | `zstd_safe::DCtx::decompress_stream` | zstd-safe ≥8.2.0 |
| 2026-0410 | zstd-sys wasm32 malloc/free shim | zstd-sys ≥2.1.2 |

**不可修**：`pingora-header-serde 0.9.0` 锁 `zstd ^0.13.1` + `zstd-safe ^7.1.0`，
这两条线**没有补丁版本**；`cargo search pingora` 实测最新就是 **0.9.0**（当前版本）
⇒ 无升级路径。
**不可达**：grep pingora 全树，三个符号命中均为 0（header-serde 只用
`zstd::dict` + `CCtx/DCtx::create` + `decompress_to_buffer`）；0410 仅 wasm32。

### ⚠️ 失败的方法论（务必记住）
想把"符号不在二进制里"当硬证据：
1. `llvm-nm` 查 PE 符号 → 三个符号全 0，看着完美；
   **但对照组（确定被调用的 `decompress_to_buffer`）也是 0** ⇒ 方法对 PE 无效。
2. 改 PDB 字符串搜索后对照组成立（8），但 `with_context`(8)/`Seekable`(1)
   是**通用名污染**（`with_context` 实际来自 anyhow）。
⇒ 结论：**任何"未命中即安全"的检查，必须先跑一个必然命中的对照**。
最终证据只认源码级调用图。

### deny.toml
4 条 ignore，每条写「不可修 + 不可达」理由。
`unused-ignored-advisory = "deny"` 保证上游一修就自动报错
（实测注入不命中的 advisory ⇒ `error[advisory-not-detected]`）。

### 门禁改进：三次迭代，前两次都错
1. 裸跑 `cargo audit` 非 0 即红 ⇒ 离线机器**永远红**。
2. 字符串匹配网络错误 ⇒ **不稳定**（同机同代码时绿时红）。
3. **现行**：`--no-fetch --stale -d <deny 的库> --ignore <从 deny.toml 读>`。
   - 两个工具**默认库不是同一个**：deny 用 `~/.cargo/advisory-dbs/advisory-db-<hash>`，
     audit 默认 `~/.cargo/advisory-db`（本机是**旧快照**，连 0391 都没有）
     ⇒ 不指定会让 audit 给出「0 漏洞」的**假绿**，比不跑更危险。
   - audit 不读 deny.toml ⇒ 豁免清单必须从 deny.toml 读，否则两份必然漂移。
   - 离线后失败原因只剩真漏洞 ⇒ 非 0 即红，不必猜字符串。
   验证：3/3 稳定 exit 0；删 0410 的 ignore ⇒ 判红并指名。

## 2026-11-01 步骤 69：render() 拆分 + 抓出 /metrics 整次抓取作废的真实缺陷 ✅

### 做法：行为敏感重构的正确姿势
1. **先建黄金快照**把当前输出钉住（`golden_render_full_exposition`，215 行逐字节），
   用**确定性状态**（不调 `mark_sink_ok`——内部取当前时间；不设 free 节点年龄——

2. **变异验证快照有判别力**（改一个字符 `4xx`→`4XX` ⇒ 判红）。
3. 按**连续行段**切成 7 段（不重排任何语句），拆完快照**一字未改地通过**。

### ⭐ 快照当场抓出的真实缺陷（生产级）
`proxy_stage_duration_ms` 的 `# HELP`/`# TYPE` 写在 per-stage 循环**内部**，
3 个 stage 输出 3 份。Prometheus 文本格式规定同一指标名只能有**一条** HELP；
违反时抓取端解析失败并**丢弃整次抓取** —— 不是丢一个指标，是**该实例所有指标一起丢**。

**官方工具实测**：`promtool check metrics`（prom/prometheus:v2.53.0）报
`text format parsing error in line 76: second HELP line for metric name
"proxy_stage_duration_ms"`。把 HELP/TYPE 提到循环外后**解析通过**。
（promtool 用的是 `docker run --rm -i --entrypoint promtool` + 从 stdin 读；
注意 Git Bash 下要先转 LF，否则报 `unknown metric type "counter\r"`。）

修后只剩命名 lint（`_total` 后缀、`_ms` 缩写）——**既有对外契约**，
Grafana 面板与告警规则依赖，改名会破坏下游，故不动。

### 补第二条测试
`each_metric_has_single_help_and_type`：按名字计数，对**任何**指标族成立。
黄金快照只抓得住"已发生的那一处"，这条抓"以后新增族时又犯一次"。

### 过程教训
抽 `populated_registry()` 共享助手时**只替换了构造函数、没删测试体里原有的状态语句**
⇒ 状态施加两次 ⇒ 快照判红。靠 `--nocapture` 对照才定位。
**这类"抽助手只替换一半"的错误，只有逐字节快照能立刻抓住**，片段断言会放过。
