# 选路决策质量基线 / Routing Baseline

> 本文件回答一个此前**完全没被回答**的问题：**选路选得好不好**。
>
> 与 [`QUALITY_BASELINE.md`](QUALITY_BASELINE.md) 的分工：
> - `QUALITY_BASELINE.md` = 工程质量的数字（测试数、门数、性能），由 `check_doc_consistency.py` 在 CI 校验
> - **本文件 = 决策质量的数字**（成功率、可避免失败、与上界的差距），由 `tools/routing_replay.py` 产出

---

## 1. 为什么需要这份基线

在 OPT-R18 之前，选路的所有验收都只证明「**选得动**」：

| 已有验收 | 证明 | 未证明 |
| --- | --- | --- |
| OPT-R13 的 1500 次活流量（3/3 命中） | 不永久锁死 | 成功率是否优于轮询 |
| 步骤 41 的 45.9% free 成功率 | 供给可用 | 换策略后是否更好 |
| `--release bandit` 17 个测试 | 数学正确、<200ns | 线上收益 |

缺这一层时，「这次改动让选路变好了吗」只能靠作者自述。本文件提供可复现的对比口径。

---

## 2. 方法：基于日志的离线策略评估

历史遥测只记录「当时选中的节点」及其结果，**没有反事实**。所以回放必须两步：

```
① 用日志拟合结果模型   P(成功 | 节点, 域名)、期望时延
② 让各策略在该模型上决策，采样结果，算 reward（与生产 compute_reward 同口径）
```

### 2.1 结果模型的两级收缩

`(节点,域名)` 的观测可能只有 1~2 条，直接取 1/1 = 100% 会让策略做出与线上无关的
乐观决策。故按 `(节点,域名) → 节点全局 → 全局` 逐级收缩，先验强度 `PRIOR_STRENGTH = 5`
（观测 <5 次时先验主导，>20 次后先验影响 <20%）。

### 2.2 必须写明的三个偏差

1. **支持偏差**：记录策略从未探索过的 `(节点,域名)` 组合只能靠先验兜底。因此
   **绝对值不是线上成功率预测**，只有策略间的**相对排序**有意义。
2. **相关当因果**：模型学的是「日志策略选它时它成功了多少次」，不是「换策略选它也
   会成功」。节点被选中本身与域名难度相关。
3. **奖励用采样而非期望**：用期望会抹掉方差、让所有策略的成功率趋同而失去区分度；
   采样保留「某节点在某域名上就是不稳」的真实形态。种子固定 ⇒ 可复现，且同一
   seed 下各策略看到同一批随机数，对比公平。

> 结论：本工具的定位是**回归护栏 + 方向判断**，不是线上收益预测器。
> 报出「LinUCB 62%」时，正确读法是「比轮询高 22 个百分点」，不是「线上会是 62%」。

## 3. 怎么跑

```bash
# 离线样本（CI 用，不依赖任何服务）
python3 tools/routing_replay.py --source jsonl --path tools/replay/sample_trace.jsonl

# 真实遥测（最近 24h）
python3 tools/routing_replay.py --source ch --hours 24 --ch-url http://127.0.0.1:8123/

# 自检：不变量断言（确定性 / 区分度 / LinUCB 必须优于轮询）
python3 tools/routing_replay.py --self-test

# 跨语言一致性门（Python 镜像 vs Rust 生产实现）
python3 tools/check_replay_parity.py --self-test
```

参数：`--policies round_robin,weighted,linucb,oracle`、`--seed`、`--format json`。

### 3.1 四个策略各代表什么

| 策略 | 含义 | 用途 |
| --- | --- | --- |
| `round_robin` | 轮询 | 无状态下限；回答「LinUCB 到底比最笨的策略强多少」 |
| `weighted` | 加权随机（权重未知时按均匀） | 生产桶快路径的形态；是加权随机的**下限** |
| `linucb` | **生产策略的镜像** | 被评估对象 |
| `oracle` | 每步选模型里成功率最高的节点 | **作弊上界**，不可部署；用来量化「还差多远」 |

## 4. 当前基线（合成样本，2026-10-27）

> ⚠️ **这不是生产基线**。`tools/replay/sample_trace.jsonl` 是**合成**的 600 条请求
> （3 个 WAF 风险不同的域名 × 4 个节点，每个域名有一个明显更好的节点）。
> 它存在的意义是：让工具本身可被 CI 验证、让读者理解报表口径。
> 真实基线须在部署环境跑 `--source ch` 后回填本节。

```
样本 600 条 / 4 节点 / 3 域名 / 结果模型全局成功率 29.7% / seed 20261027
```

| 策略 | 成功 | 成功率 | 平均奖励 | 可避免失败 | P50 时延 | P99 时延 | 命中节点数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `round_robin` | 178/600 | 29.7% | 0.4096 | 385 (64.2%) | 222ms | 447ms | 4 |
| `weighted` | 185/600 | 30.8% | 0.4191 | 394 (65.7%) | 172ms | 447ms | 4 |
| `linucb` | 313/600 | 52.2% | 0.5753 | 180 (30.0%) | 115ms | 249ms | 4 |
| `oracle` | 462/600 | 77.0% | 0.7544 | 0 (0.0%) | 149ms | 249ms | 3 |

### 4.1 这张表说明什么

1. **LinUCB 确实在学习**：比轮询高 **22.5 个百分点**，比加权随机高 21.4pp。
   这不是"能跑"，是"选得更好"——此前没有任何数字能证明这一点。
2. **离上界还很远**：52.2% vs oracle 77.0%，**差 24.8pp**。也就是说，
   在「该域名该用哪个节点」这件事上，还有约 1/4 的流量被选错了。
   这是下一轮选路优化的**具体目标**，而不是笼统的"继续调 alpha"。
3. **可避免失败仍有 30%**：180 条请求选中的节点失败、而候选里存在成功率 ≥50% 的
   其他节点。这是最该优化的那一类失败——不是网络差，是选错。
4. **P99 时延已接近 oracle**（249ms vs 249ms），说明瓶颈不在尾部延迟，
   而在**成功率**。调优方向应是「少选错」，不是「选快」。

## 5. 使用规则（准入）

选路相关改动（`bandit.rs` / `router.rs` 的选路分支 / 权重策略）合并前，PR 描述必须附：

1. `python3 tools/routing_replay.py --source ch --hours 24` 的**改动前后两张表**；
2. 一句结论：哪个指标动了、为什么；
3. 若成功率下降而平均奖励上升，必须解释原因（可能是换了更便宜但更不稳的节点）。

**没有回放对比的选路改动不合并**——这条规则的等价物是「性能改动必须附 benchmark」。

## 6. 与代码的一致性如何保证

Python 侧是 `BanditArm` 的**镜像实现**，天然有漂移风险。两侧各有一把锁：

| 侧 | 锁 | 失败后果 |
| --- | --- | --- |
| Rust | `bandit::tests::opt_r18_replay_parity_vectors_match_fixture` | 改了公式没更新 fixture ⇒ 判红 |
| Python | `tools/check_replay_parity.py` | 镜像没跟上生产 ⇒ 判红 |

黄金向量由**生产实现自己生成**（`print_replay_parity_vectors`，`#[ignore]`），
不是手写的期望值——否则同一个理解错误会同时通过两份断言。当前两侧最大差异
`3.33e-16`（机器精度）。门的变异自测：扰动 `alpha` 1e-3 必须判红，证明它不是摆设。

覆盖的关键分支：fresh 臂、free 溢价、`theta` 裁剪、free 档 1000 次遗忘、大 `t`、
高 WAF 风险上下文。
