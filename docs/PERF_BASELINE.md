# 端到端吞吐基线 / E2E Throughput Baseline

> 首次测量：2026-10-03（OPT-R16 B）。此前项目**没有任何端到端性能数据**，
> 只有选路微基准（2000 候选 ~78ns/op）。本文件记录首个可复现的容量基线。
>
> 复现：`python tools/bench_gateway.py`（一键：编译 → 起上游 → 起网关 →
> 测地板 → 就绪门 → 阶梯压测 → 收摊）。工具源码见 `tools/bench/main.go`。
>
> 本文件只记录**吞吐与成功率**。测试数/门数等质量数字以
> [`QUALITY_BASELINE.md`](QUALITY_BASELINE.md) 为准。

---

## 1. 结论（先说）

| 项 | 值 |
| --- | --- |
| 实测峰值 | **17,215 QPS** @ conc=4，成功率 100% |
| 持续整形吞吐 | **~10,000 成功 QPS**（超出部分被正确 shedding 为 429） |
| 地板（客户端+上游直连） | **191,403 QPS** |
| 瓶颈位置 | **租户限流器**（按设计工作），不是代理路径 |

解读：网关已证明能承载 17k+ QPS 且零失败；持续负载下限流器按
`TENANT_SENTINEL_QUOTA = 10_000`（编译期常量，`tenant.rs:100`）把成功吞吐
整形到 10k，超出的请求返回 429 而不是超时/崩溃。**429 在这里是正确的
shed 行为，不是故障**——状态码分布证明了这一点（见 §3）。

网关的**裸产能**（不限流时）高于 17k，但尚未测到：burst 窗口内的短跑
最高只到 17,215 QPS 即 100%，而持续跑会被限流器先截住。要测裸产能需
给租户配额加环境变量覆盖（当前是 const），列为后续工作，不在本轮范围。

## 3. 实测数据

### 3.1 地板（客户端 → 上游直连，不经过网关）

| 并发 | QPS | 成功 | p99 |
| --- | --- | --- | --- |
| 64 | 99,803 | 12,800/12,800 (100%) | 3.24ms |
| 256 | 191,403 | 51,200/51,200 (100%) | 8.24ms |

地板 ≈ 191k QPS，是端到端峰值的 **11 倍** ⇒ 端到端数字确实是网关自身的
产能，客户端与上游都不是瓶颈。

### 3.2 端到端（客户端 → 网关 → 上游）

| 并发 | QPS | 成功率 | 状态码分布 | p99 |
| --- | --- | --- | --- | --- |
| 1 | 6,779 | 300/300 (100%) | 200:300 | <0.5ms* |
| 4 | **17,215** | 1,200/1,200 (100%) | 200:1200 | <0.5ms* |
| 16 | 11,703 | 3,388/4,800 (70.6%) | 200:3388 **429:1412** | 2.29ms |
| 32 | 10,157 | 8,859/9,600 (92.3%) | 200:8859 **429:741** | 7.03ms |
| 64 | 10,100 | 14,957/19,200 (77.9%) | 200:14957 **429:4243** | 13.83ms |
| 128 | 10,069 | 27,594/38,400 (71.9%) | 200:27594 **429:10806** | 16.78ms |
| 256 | 10,041 | 56,265/76,800 (73.3%) | 200:56265 **429:20535** | 35.87ms |

（`*` 见 §5 时钟分辨率说明。）

观察：
- conc=1/4：100% 成功，QPS 随并发上升 ⇒ 网关路径本身健康。
- conc≥16：成功 QPS 收敛到 ~10k，超出部分全部是 **429**（无超时、无 5xx、
  无连接错误）⇒ 限流器在按设计 shedding。
- 全程零 5xx、零超时、零连接错误 ⇒ 高负载下无崩溃、无级联失败。

## 4. 瓶颈分析

```
客户端 (191k) → 网关代理路径 (≥17k 实测) → 租户限流 (10k 整形) → 上游 (191k)
                                              ▲
                                         瓶颈在此（按设计）
```

- **代理路径**（选路+转发）：至少 17k QPS，100% 成功。真实上限未知，
  被限流器挡住没测到。
- **限流器**：`Quota::per_second(10_000).allow_burst(...)`，短跑可在 burst
  窗口内冲到 17k，持续跑收敛到 10k。这是**策略**，不是性能上限。
- **上游/客户端**：191k 地板，11 倍余量，无影响。

## 5. 已知测量局限（诚实标注）

### 5.1 本机 Go 时钟粒度 ~0.5ms，亚毫秒延迟不可信

实测（`clockprobe`，20 万次连续 `time.Now()` 调用）：199,999 次返回
**完全相同的值**，最小正增量 519,700ns。而 Python 的 `perf_counter`
在同一台机器上是 100ns 粒度、零重复值。

后果：
- **QPS 与成功率可信**（墙钟，秒级区间，不受影响）。
- **p50/mean 低于 ~0.5ms 时显示为 0**（如 `p50=0s`），那是时钟量化，
  不是"零延迟"。本文件 p99 取毫秒级尾部，大致可信；p50 一律记为
  `<0.5ms（低于本机计时分辨率）`，不作为事实引用。
- 若将来在 CI 加延迟断言，必须用毫秒级粗阈值，或在 Linux runner 上跑
  （待验证其时钟是否正常）。

### 5.2 单进程 + 回环 + 遥测关闭

- 测的是**单核代理开销**，不是集群容量。
- 遥测到 Redis/ClickHouse 关闭 ⇒ 这是部署**下限**，开了遥测只会更慢。
- 上游是极简 handler；真实代理节点会引入额外延迟与自身吞吐上限。
- 开发机绝对值不可直接当生产容量；可移植的是**方法、地板对比法、
  与"限流器先于代理路径饱和"的结构性结论**。

### 5.3 一次未完全解释的异常（已记录在案）

编排脚本早期版本曾出现"低并发全失败（0%）、高并发部分恢复（72%）"的
反常曲线，而同样参数手工执行 100% 成功。事后确认了两个 contributing factor：

1. 旧脚本用 `/metrics` 可达即判"网关已起"，但 8916 监听实际上晚于
   8917（就绪门第一轮 attempt 抓到过 `connectex: actively refused`）。
   现已加 `wait_ready()`：用与压测完全相同的路径打小批量，
   连续 3 次 10/10 才放行。
2. 旧地板测量误把 target 写成网关端口，导致 floor 实际走的也是网关。

两者都已修复并验证（本次基线即新流程产出）。但**当时那条反常曲线本身
没有被完整复现解释**——它是"启动窗口 + 测量错误"的叠加态，而我没有保留
当时的网关日志（被后续运行覆盖）。`start_gateway` 现已归档上一次的
`gw.err` 为 `.prev`，避免重蹈。

## 6. 后续工作

1. **裸产能测量**：给 `TENANT_SENTINEL_QUOTA` 加环境变量覆盖，
   在不限流下测代理路径的真实上限（预计显著高于 17k）。
2. **遥测开启后的对比**：起 Docker（Redis+ClickHouse），量化遥测链路
   对吞吐的影响。
3. **Linux runner 复测**：验证时钟是否正常，拿到可信的 p50。
4. **压测进 CI**：当前压测需起进程、不适合每次 PR 跑；可考虑 nightly
   定时跑 + 结果回归比对（QPS 跌超阈值即告警）。
