## 0. 本报告的取证纪律

撰写过程中，本报告的首版被发现含 **6 处错误**（含 2 处会直接误导使用者），已全部更正并留档于 §2。

从中得到的硬规则，后续任何能力声明都必须遵守：

| 规则 | 反面教材 |
| --- | --- |
| 数测试/函数前，**先确认正则覆盖了目标语法** | 用 `pub fn` 数函数，漏掉 `async fn`，把「4 个测试」误报为「0 个测试」 |
| 列为「可配置项」前，**确认它是 `env` 读取而非 `const`** | 把 `const TIER_QUOTA_WINDOW: usize = 100` 当环境变量写进 usage |
| 引用实测数字前，**确认它有文档留痕** | 「通过率 0.65%」实为自行推算，无任何文档依据 |
| 能力归因到文件前，**确认符号真的在那个文件里** | 把 402 计费归给 `tenant.rs`，实际在 `gateway.rs` |
| 能力状态只写**已验证 / 部分 / 缺失**三档 | 用「完整 ✅」掩盖「纯被动、无主动探测」这类关键限定 |

## 1. 产品定位

**企业级 HTTP/SOCKS 正向代理网关**。核心差异点是**出口节点自学习选路**：用 LinUCB 多臂老虎机按 `(目标域名上下文 × 节点历史表现)` 实时打分选节点，而非静态轮询或加权随机。

**它不是**：代理池聚合器（不签发订阅链接）、不是爬虫防护绕过服务、不是匿名住宅代理服务商（不自带 IP 资源）。

## 4. 能力边界（部分完成）

这一节是本报告的重点：**「有」不等于「够用」**。

| 能力 | 实际边界 | 后果 |
| --- | --- | --- |
| 被动隔离 | **无主动健康探测**，纯靠真实流量喂信号 | 空闲节点永不触发隔离；坏节点要等被选中才暴露 |
| 性能 | 端到端基线见 [`PERF_BASELINE.md`](PERF_BASELINE.md)：峰值 17,215 QPS（100%），持续负载被限流器整形到 ~10k（429 shedding） | 选路微基准不能推断 QPS；裸产能（不限流）尚未测到，见 PERF_BASELINE §6 |
| 协议 | 不支持 HTTPS 入站 | 浏览器/移动 App 不能直接接入 |
| 多租户 | 租户表在内存，重启丢失 | 无持久化，重启后需重新注册 |
| 分档探索配额 | 窗口 100 为经验值，未调优 | 且**修改后未做活流量分布回归**（仅单测） |
| GeoIP | 无 mmdb 时退化为 Disabled | 匿名度/地域校验静默失效 |

| 能力 | 状态 |

## 5. 与同类软件的差距

对标两组：**开源代理软件**（Squid / Tinyproxy）与**商业代理基础设施**（Bright Data / Oxylabs / IPRoyal）。

> 注：后两者是「代理服务商」形态（售卖 IP 资源），与本项目不同赛道，对比仅用于说明护城河差异。

| 维度 | 本项目 | Squid / Tinyproxy | 商业代理基础设施 | 判定 |
| --- | --- | --- | --- | --- |
| 出口选择智能度 | LinUCB 自学习 | 静态轮询 / 权重 | 商业级 ML 调度 | **领先开源同类** |
| 免费池自建供给 | ✅ 多源 + 分级验证 | ❌ 依赖用户自配 | ⚠️ 自有 IP 池 | **特色能力** |
| 协议完备度 | ⚠️ 无 HTTPS 入站 | ✅ 含 HTTPS 入站 | ✅ 全协议 | **落后 1 档** |
| 可运维性 | ⚠️ 31 指标 + 15 告警，但**无控制台 / 无热更新** | ✅ Web 管理 + SNMP | ✅ SaaS 控制台 | **落后 2 档** |
| HA / 多活 | ⚠️ 有跨实例隔离扇出，**无集群调度** | ✅ 多缓存模式 | ✅ 分布式集群 | **落后 2 档** |
| 认证体系 | ⚠️ 静态 Key + 内存租户表 | ✅ LDAP / PAM / file | ✅ 用户 / 团队 / 计费 | **落后 2 档** |
| 测试与门禁 | 284 单测 + 12 门 + CI | ⚠️ 有测试，覆盖率未知 | ✅ 商业级 QA | **领先** |
| 合规 | ✅ 免费档零信任、MaxMind 署名 | ⚠️ 视部署 | ✅ 全套 | **特色** |
| IP 资源规模 | ❌ 依赖公开免费源 | ❌ 无 | ✅ 数百万 IP | **结构性劣势** |

### 三个本质差距

**① 没有 IP 资源护城河（赛道问题，非工程问题）。**
核心壁垒是「稳定的大规模 IP 池 + 合规采购」。本项目依赖公开免费源，
外部供给随公网源质量波动。一旦免费源枯竭或收紧，价值立刻归零。

**② 生产就绪度缺「最后一公里」。**
缺控制台、缺配置热更新、缺集群调度、缺主动探测。
使用者当前必须**改环境变量 → 重启进程 → 查日志**来运维，与「企业级网关」定位不匹配。

**③ 协议与场景覆盖窄。**
无 HTTPS 入站意味着浏览器/移动 App 不能直接用；
无 PAC 分发意味着多端接入只能靠环境变量。这是「能否被真实企业采用」的分水岭。

### 不应低估的客观优势

1. **LinUCB 选路是真实差异化**，不是概念包装。多数开源代理池是「轮询 + 健康检查」；
   本项目按 `(域名上下文 × 节点表现)` 学习，在「某域名对某出口敏感」这类真实场景能提升成功率。
2. **工程严谨度高于常见个人开源项目**。12 个静态门多数做过**双向验证**
   （把阈值调到极端值确认门会红），`check_promql_metrics.py` 能抓出
   PromQL 函数名被误当指标的假阳性——这类门通常只有大厂才有。
3. **免费档零信任是合规加分项**。免费代理承载凭据流量是真实事故源，
   本项目在网关层强制 403，多数同类不做。
4. **免费池供给侧自建能力**。分级验证 + 多源调度 + 零产出自动 suspend，
   是不依赖外部服务的独立工程量。

## 7. 已知局限（诚实标注）

本报告刻意保留以下不确定性，不做粉饰：

1. **免费池供给规模无法复现核实**。45.9% 成功率有 `EXEC_LOG.md` 留痕，
   但「一轮抓取 → 入池 N 个」类数字文档中不存在，不应当作实测结论引用。
2. **端到端性能已有首个基线**（OPT-R16 B，见 [`PERF_BASELINE.md`](PERF_BASELINE.md)）：
   峰值 17,215 QPS @ 100%，持续负载被限流器整形到 ~10k（429 shedding）。
   但注意其适用范围：单进程 + 回环上游 + 遥测关闭，且本机 Go 时钟粒度
   ~0.5ms 使亚毫秒 p50 不可信（详见 PERF_BASELINE §5）。
   「裸产能（不限流）」与「遥测开启后的对比」仍无数据，见 PERF_BASELINE §6。
3. **不做完成度打分**。首版曾给出「核心 95% / 协议 55% / 运维 25%」等百分比。
   这些是主观判断，无统一量表、不可复核，故本版**删除**。
   §3 / §4 的「已验证 / 边界 / 缺失」三档是可取证的事实陈述，替代打分。

## 8. 路线建议

**若目标是「能用的内部工具」** → 已达成，停止投入即够用。

**若目标是「企业级网关」** → 按价值排序：

1. **控制面 API + 配置热更新** — 解锁运维可运维性（当前最大短板）
2. **HTTPS 入站 + PAC 分发** — 解锁真实企业接入场景（浏览器/移动端）
3. **主动健康探测** — 补齐隔离闭环（当前纯被动）
4. **租户/配额持久化** — Redis 已有，成本低
5. **端到端吞吐压测** — 当前完全无数据，是隐性风险
6. **分档配额的活流量分布回归** — 修改后未做真实池验证

**若目标是「商业产品」** → 需重新评估赛道：
没有 IP 资源护城河时，工程优势难以变现。
